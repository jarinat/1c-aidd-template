# Итоговый отчёт baseline — 2026-07-22

## Вывод

В первой серии `edt-mcp` оказался наиболее эффективным для BSL, запросов и
обычного typed metadata: меньше времени, ходов и MCP-вызовов в большинстве
quality-valid write операций. Это не делает его универсальным default.

Для изменения форм корректный итог дали `edt-companion-mcp` и `1c-rsv`; у
`edt-mcp` был создан только реквизит формы с пустым type и без bound field.
Cleanup через `edt-mcp` превысил 180 секунд, тогда как companion и RSV удалили
свои fixtures штатно.

## Что проверял каждый сценарий

### Read-only

| Сценарий | Проверяемое действие | Корректный результат |
|---|---|---|
| `workspace-discovery` | Найти открытый EDT workspace и точное имя проекта | Найден существующий workspace, project name не угадан, а подтверждён server response |
| `metadata-details` | Прочитать structural details известного metadata object | Верный FQN, вид объекта и доступная структура; без изменения model/source |
| `bsl-method` | Найти и прочитать существующий BSL method | Верный модуль, method, границы строк и исходник метода. Это **чтение**, а не написание BSL-кода |
| `method-references` | Найти semantic references, callers/callees выбранного метода | Структурированный результат поиска либо честный пустой результат; literal search не выдаётся за semantic analysis |
| `form-structure` | Прочитать состав управляемой формы | Подтверждённое существование формы, её реквизиты и элементы; отдельно фиксируется, если renderer не даёт visual data |
| `query-validation` | Проверить текст запроса к metadata проекта | `valid`/diagnostics и явно указанный режим: project-aware или только syntax validation |

### Write fixtures

Все write-сценарии работали только с временными объектами уникального
benchmark prefix и после серии были удалены. Для любого write результата
проверялся фактический source/metadata, а не только финальный текст Claude.

| Сценарий | Проверяемое действие | Корректный результат |
|---|---|---|
| `write-create-commonmodule` | Создать server-only CommonModule | Объект существует, `server=true`, нет незаказанных application contexts |
| `write-add-method` | Добавить экспортный `GetStatus()` | В модуле есть ровно ожидаемая функция с литералом `v1` |
| `write-modify-method` | Точечно заменить `v1` на `v2` | Сначала прочитан актуальный source, затем изменён только нужный литерал; `v1` отсутствует, `v2` есть |
| `write-add-query` | Добавить функцию с текстом запроса | Существующий метод сохранён, добавлена только ожидаемая query function |
| `write-modify-query` | Добавить условие в существующий query | Изменён только query, итог прошёл доступную validation, существующий BSL сохранён |
| `write-create-processor` | Создать временный DataProcessor | Объект создан через typed API и структурно перечитан |
| `write-create-form` | Создать управляемую форму обработки | Форма существует и подтверждена structural read-back |
| `write-add-form-field` | Добавить String attribute и bound input field | Есть String value type, реквизит и связанный `FormField`; один реквизит без элемента не считается полным успехом |
| `cleanup-fixture` | Удалить временные CommonModule и DataProcessor | Fixtures отсутствуют одновременно в metadata и source; timeout cleanup фиксируется как отдельный результат |

## Маршрутизация по baseline

- BSL, queries, обычное metadata: `edt-mcp` + обязательный read-back.
- Forms: `edt-companion-mcp`; RSV — fallback.
- Cleanup/delete: companion предпочтительнее.
- Project-aware query validation: `edt-mcp` или RSV; companion в этой серии
  работал только как syntax validator.

## Качественные наблюдения

- `edt-mcp` при создании server-only CommonModule добавил лишние application
  contexts и сообщил о корректном результате в финальном тексте. Post-check
  обязателен.
- RSV создаёт локальный backup BSL при записи: это side effect, который надо
  учитывать в cleanup и Git diff.
- Формат BSL/query может различаться при семантически равном результате;
  проверка должна быть structural, а не основанной только на текстовом diff.

## Ограничения

Серия содержит по одному fresh-Claude sample на операцию. Cache и skill context
существенно влияют на токены. Для смены routing нужен повтор critical операций
минимум три раза с медианами и неизменной методикой.

# Задание Hermes: корпоративный agent layer для 1С/EDT

Ты — Hermes, ведущий инженер и оркестратор эксперимента по созданию общего
слоя инструкций для ИИ-агентов в 1С/EDT-проектах MPL Systems.

Твоя задача — исследовать, спроектировать, реализовать и практически проверить
корпоративный agent layer, одинаково пригодный для Claude Code и Codex.

Работай автономно. Это прямое подтверждение пользователя на исследование,
изменение agent layer в пилотном репозитории, локальные эксперименты и создание
коммитов в границах, заданных ниже. Не запрашивай повторное подтверждение для
обычных действий внутри этих границ.

Не останавливайся после проектирования или первой реализации. Используй Claude
CLI и Codex CLI как независимых архитекторов, исполнителей и проверяющих,
собирай фактические результаты, исправляй архитектуру и повторяй испытания до
качественного результата либо до объективного внешнего блокера.

## Репозитории и их роли

Все пути указаны внутри окружения Hermes.

### Корпоративный шаблон — только чтение

```text
/workspace/git/sollers/hermy-EDT-project-template
```

Это корпоративный продуктовый baseline. По нему определяй:

- структуру 1С/EDT-проекта;
- штатные scripts и CI;
- существующие тестовые механизмы;
- структуру документации;
- способ будущей доставки agent layer в рабочие проекты.

Не изменяй этот репозиторий, его ветки, индекс и рабочее дерево.

### Личный шаблон — только чтение и извлечение опыта

```text
/workspace/git/my-projects/hermy-1c-aidd-template
```

Это донор накопленных инженерных практик для 1С, EDT, YAxUnit, review, Sonar и
Git. Используй его для поиска качественных правил, справочников, проверок,
skills и scripts, но не как готовую архитектуру корпоративного слоя.

Не изменяй этот репозиторий, его ветки, индекс и рабочее дерево.

### Пилотный проект — реализация и проверка

```text
/workspace/git/sollers/hermy-PROSYS-Avtolid
```

Это единственный репозиторий, где разрешены изменения и коммиты. Все
корпоративные файлы реализуй и проверяй здесь. Итоговые коммиты должны быть
пригодны для последовательного cherry-pick в корпоративный шаблон.

Если фактические пути в контейнере отличаются, сначала найди эти три
репозитория внутри `workspace/git`, проверь их корни и remotes. Не подменяй их
одноимёнными репозиториями вне workspace Hermes.

## Исходная ситуация

Перепроверь фактическое состояние перед началом. Не считай следующие сведения
неизменными:

- `hermy-EDT-project-template` изначально не содержит общего agent layer;
- в пилоте может существовать игнорируемый `.claude/` с персональными
  настройками и workflow;
- в пилоте могут существовать персональный `AGENTS.md`, `aidd/`, `.mcp.json`,
  локальные scripts и другие незакоммиченные файлы;
- `.claude/` в пилоте на момент постановки задачи целиком игнорировался через
  `.gitignore`;
- в рабочем дереве пилота могут быть пользовательские изменения, не связанные
  с этой задачей.

Сначала прочитай применимые `AGENTS.md` и другие инструкции во всех трёх
репозиториях. Инструкции двух read-only репозиториев учитывай при исследовании,
но не воспринимай как разрешение на их изменение.

Перед любой правкой в пилоте зафиксируй:

- абсолютный корень репозитория;
- текущую ветку и HEAD;
- `git status --short`;
- tracked, untracked и ignored agent-related файлы;
- правила `.gitignore` и `.git/info/exclude` для `.claude`, `.agents`,
  `AGENTS.md`, локальных дополнений и временных результатов;
- доступные версии `claude`, `codex`, `git`, PowerShell, shell и OneScript;
- имена настроенных MCP без вывода секретов.

Сохрани существующие пользовательские изменения. Не удаляй, не перезаписывай,
не откатывай и не включай их в свои коммиты.

Если корпоративной реализации требуется путь, уже занятый персональным файлом,
не перезаписывай его молча. Сначала сохрани его эффективные персональные
инструкции в выбранном локальном расширении, затем докажи, что персональный
слой продолжает работать и не попал в Git.

## Цель

В пилотном проекте создай корпоративный слой, который после проверки можно
перенести в `hermy-EDT-project-template` обычными cherry-pick.

Слой должен:

1. Работать с Claude Code и Codex.
2. Содержать общие правила разработки 1С/BSL и EDT.
3. Предоставлять атомарные skills для типовых инженерных задач.
4. Не зависеть от персонального workflow, модели, подписки или конкретного
   разработчика.
5. Не содержать AIDD, его lifecycle, artifacts, роли, routing или скрытые
   предположения.
6. Позволять разработчику добавлять собственные локальные инструкции, skills,
   MCP и настройки поверх корпоративного слоя.
7. Не заставлять команду вручную поддерживать две расходящиеся копии одного
   процесса для Claude Code и Codex.
8. Разделять корпоративные стандарты, подтверждённые правила конкретного
   проекта и персональные дополнения.
9. Быть пригодным для будущего обновления из общего EDT-шаблона без
   перезаписи личного слоя.
10. Поддерживаться автоматической структурной валидацией и реальными
    испытаниями обоих CLI.

## Непересекаемые границы

- Не изменяй `hermy-EDT-project-template`.
- Не изменяй `hermy-1c-aidd-template`.
- Не делай `push`, merge request и записи во внешние системы.
- Не включай в коммиты `.mcp.json`, секреты, токены, персональные настройки,
  временные worktree, CLI-транскрипты и результаты тестовых запусков.
- Не включай существующие пользовательские изменения в свои коммиты.
- Не используй `git add .`, `git add -A` и другие широкие операции staging.
- Не изменяй бизнес-логику проекта ради демонстрации skills. Для экспериментов
  используй временные файлы, fixtures, отдельные ветки или worktree.
- Не запускай тесты против рабочей или неизвестной информационной базы.
- Не выводи значения токенов, credentials и секретных параметров.
- Не считай текстовую инструкцию технической гарантией там, где свойство можно
  проверить validator, тестом, анализатором или CI.

Широкая автономия разрешена внутри этих границ: можно создавать временные
ветки и worktree, использовать сеть и официальную документацию, устанавливать
необходимые локальные инструменты, запускать Claude CLI и Codex CLI, создавать
fixtures и многократно перерабатывать реализацию.

## Обязательный namespace

Все корпоративные skills обязаны иметь префикс `mplsys-`.

Минимальный набор имён:

- `mplsys-1c-query`;
- `mplsys-yaxunit`;
- `mplsys-edt-mcp` либо обоснованно разделённые EDT MCP skills;
- `mplsys-code-review`;
- `mplsys-address-review`;
- `mplsys-fix-sonar`;
- `mplsys-commit`;
- `mplsys-project-onboarding`.

Если разные EDT MCP действительно требуют самостоятельных контрактов,
используй имена:

- `mplsys-edt-mcp`;
- `mplsys-edt-companion-mcp`;
- при подтверждённой необходимости — `mplsys-1c-rsv`.

Одинаковое логическое имя используй для канонического skill и его
tool-specific адаптеров. Корпоративный namespace должен быть защищён от
случайного shadowing личными или проектными skills.

Для связанных технических файлов предпочтителен тот же namespace:

```text
.agents/skills/mplsys-*/
.claude/skills/mplsys-*/
.claude/rules/mplsys/
tools/ai/mplsys-*.ps1
tools/ai/mplsys-*.sh
```

Это предпочтительная схема именования, а не требование слепо создать все эти
каталоги. Фактическую архитектуру обоснуй возможностями обоих CLI.

4. Проверь актуальность API и команд.
5. Адаптируй для Claude Code и Codex.
6. Проверь независимо через оба CLI.
7. Убедись, что результат понятен без знания личного шаблона.

Итоговый корпоративный слой не должен ссылаться на
`hermy-1c-aidd-template`.

## Архитектурное исследование

До реализации поручи Claude CLI и Codex CLI независимо проанализировать
задачу. Дай им одинаковый фактический контекст, но не показывай выводы друг
друга.

Попроси каждого предложить:

- layout корпоративных правил и skills;
- единый source of truth при поддержке двух CLI;
- механизм Claude-адаптеров, если он требуется;
- механизм проектного и персонального расширения;
- selective tracking корпоративных файлов внутри `.claude`, которая сейчас
  может быть целиком в `.gitignore`;
- правила сосуществования корпоративного `AGENTS.md`, личного Codex-слоя и
  персонального `.claude`;
- способ обнаружения skills обоими CLI;
- защиту namespace `mplsys-` от конфликтов;
- способ будущего обновления слоя из EDT-шаблона;
- автоматическую проверку архитектурных инвариантов.

Самостоятельно сравни предложения с актуальными возможностями установленных
CLI. Используй `claude --help`, `codex --help`, фактическое поведение и при
необходимости официальную документацию. Не принимай утверждение агента как
факт без проверки.

Рассмотри как минимум следующие архитектурные варианты:

1. Канонические skills в `.agents/skills` и тонкие Claude-адаптеры.
2. Канонические skills в другом общем каталоге с адаптерами для обоих CLI.
3. Две генерируемые tool-specific проекции из одного источника.
4. Полностью независимые копии — только как контрольный вариант с явной
   оценкой риска расхождения.

Выбери вариант по evidence. Зафиксируй отвергнутые варианты и причины в
итоговом отчёте, но не засоряй корпоративный runtime историей эксперимента.

Предпочтительные свойства, которые необходимо проверить, а не принять
вслепую:

- короткая корпоративная точка входа;
- каноническое содержание без двух расходящихся копий;
- тонкие tool-specific адаптеры;
- selective tracking корпоративных Claude-файлов при сохранении игнорируемых
  персональных файлов;
- явный и документированный механизм локального дополнения Codex;
- отсутствие обязательного корневого `CLAUDE.md`, если Claude надёжно
  обнаруживает корпоративный слой без него;
- устойчивый namespace;
- один source of truth для каждого правила.

## Обязательный MVP

### Общие стандарты

Подготовь корпоративные документы как source of truth минимум для:

- разработки 1С/BSL и EDT;
- стиля BSL;
- запросов 1С;
- тестирования и YAxUnit;
- code review;
- Git и коммитов;
- выбора и безопасного применения agent tools;
- разделения корпоративных, проектных и персональных правил.

Не превращай текстовые правила в замену CI, анализаторам и тестам.

Проектные факты храни отдельно от корпоративных стандартов. Персональные
предпочтения должны иметь отдельный игнорируемый Git слой.

### Требования ко всем skills

Каждый skill должен:

- решать одну чёткую задачу;
- иметь ясные triggers и границы;
- быть независимо вызываемым;
- не требовать предварительного запуска другого skill;
- не ссылаться на персональный workflow;
- не содержать project-specific имена, пути, префиксы метаданных и тикетов;
- проверять фактические версии API и инструменты, когда это существенно;
- корректно сообщать об отсутствии необязательного инструмента;
- разделять анализ, изменения и внешние побочные эффекты;
- не заявлять успешную проверку без фактического evidence;
- сохранять пользовательские изменения;
- быть применимым без знания остальных skills.

Общие standards и references можно переиспользовать, но удаление одного skill
не должно ломать остальные.

### `mplsys-1c-query`

Skill должен покрывать создание, изменение, анализ и review запросов 1С.

Проверь и отрази как минимум:

- параметры вместо конкатенации пользовательских значений;
- корректную работу с временными таблицами;
- условия соединений и влияние на кардинальность;
- nullable-поля и трёхзначную логику;
- итоги, группировки, виртуальные таблицы и периодичность;
- производительность без выдуманных универсальных оптимизаций;
- проверку полей и метаданных фактического проекта;
- сохранение семантики запроса при рефакторинге.

### `mplsys-yaxunit`

Skill должен покрывать проектирование, написание, исправление, review и
диагностику YAxUnit-тестов.

Он обязан:

- определять фактическую версию YAxUnit;
- проверять API по установленным исходникам и рабочим примерам;
- не угадывать assertions, Мокито и test data API;
- различать unit, integration и smoke-сценарии;
- требовать изоляцию и очистку тестовых данных;
- не заявлять PASS без свежего запуска и анализа результата;
- учитывать безопасность используемой информационной базы.

### EDT MCP skills

Архитектура не должна слепо предполагать один конкретный сервер.

Исследуй:

- фактическую `.mcp.json` пилота без вывода секретов;
- доступные EDT MCP tools и их schemas;
- необходимость поддержки `edt-mcp`, `edt-companion-mcp` и `1c-rsv`;
- правило выбора одного активного EDT MCP;
- безопасный fallback при отсутствии или неполном API;
- границы между MCP-редактированием и прямым изменением EDT-файлов;
- риск смешивания нескольких write-механизмов в одной операции.

Не выдумывай schema. Перед содержательным вызовом проверяй фактический tool
contract. Недоступность MCP должна приводить к понятной диагностике или
разрешённому fallback, а не к молчаливой подмене другим сервером.

### `mplsys-code-review`

Skill должен проводить review без изменения файлов.

Он должен:

- определить точный change-set и baseline;
- проверять дефекты, регрессии, безопасность, производительность и тесты;
- отличать доказанный дефект от предположения и вкусового замечания;
- ссылаться на конкретное место и объяснять последствие;
- учитывать общие и проектные правила;
- не исправлять код в read-only режиме;
- не подменять review пересказом diff или выводом анализатора.

### `mplsys-address-review`

Skill должен исправлять только явно выбранные замечания review.

Он должен:

- сохранить отклонённые и отложенные замечания без изменений;
- перепроверить фактическую применимость замечания;
- вносить минимальный fix причины;
- выполнить релевантные проверки;
- показать соответствие «замечание → изменение → проверка».

### `mplsys-fix-sonar`

Skill должен получать или принимать Sonar issues, сопоставлять их с актуальным
кодом и исправлять только подтверждённые замечания.

Он должен:

- поддерживать offline fixture без токена для базовой проверки;
- проверять project key, PR/branch и revision, когда данные доступны;
- не считать Sonar issue автоматически истинным;
- не скрывать issue без обоснования;
- не включать токены и отчёты в Git;
- отделять получение evidence от исправления кода;
- корректно работать при недоступности SonarQube.

Не захватывай существующее пользовательское изменение
`tools/scripts/download-sonar-issues.os`, если оно всё ещё присутствует и не
является осознанной частью нового атомарного изменения.

### `mplsys-commit` и commit helper

Кроме skill создай безопасный project-local helper script.

Helper должен:

- работать только с явно переданными путями;
- показывать предварительный status и diff;
- не захватывать посторонние изменения;
- поддерживать dry-run;
- отказывать при пустом или некорректном сообщении;
- не выполнять push;
- возвращать понятный exit code;
- корректно работать с путями, содержащими пробелы;
- по возможности иметь удобные точки входа для Windows и Linux либо
  документированное обоснование выбранной переносимой реализации.

Префикс `EDTPT-AI:` относится только к экспериментальным коммитам Hermes. Не
навязывай этот префикс обычным разработчикам через корпоративный helper.

### `mplsys-project-onboarding`

Onboarding должен обследовать конкретный 1С/EDT-проект и отделять:

- подтверждённые факты;
- предположения;
- открытые вопросы;
- принятые человеком решения.

Он должен изучать README, EDT-проекты, CI, анализаторы, тестовые команды,
интеграции и устойчивые примеры кода. Единичный пример не считается общим
правилом. Onboarding не должен переносить персональный workflow в
корпоративный или проектный слой.

## Расширяемость корпоративного слоя

Спроектируй три явных уровня:

1. Корпоративные обязательные стандарты и skills.
2. Подтверждённые правила конкретного проекта и path-specific ограничения.
3. Персональные локальные дополнения разработчика.

Персональный слой должен позволять добавлять предпочтения, дополнительные
skills, MCP и настройки, не требуя изменения корпоративных файлов. Он не
должен случайно скрывать корпоративные skills `mplsys-*`.

Добавь нейтральные examples персональной настройки, но не коммить реальные
персональные файлы пилота.

Обязательно проведи два сценария.

### Чистый разработчик

Создай чистый worktree или checkout только из tracked-файлов и проверь:

- Codex обнаруживает корпоративные инструкции и skills;
- Claude Code обнаруживает корпоративные инструкции и skills;
- отсутствие персонального слоя не вызывает ошибок;
- документация объясняет, куда добавлять проектные и личные настройки;
- корпоративные Claude-файлы материализуются после checkout, несмотря на
  прежнее общее правило игнорирования `.claude/`.

### Разработчик с личным слоем

Используй существующий персональный слой пилота либо его безопасную копию и
проверь:

- корпоративные правила продолжают загружаться;
- персональные инструкции действительно применяются;
- корпоративные и персональные skills сосуществуют;
- одинаковые имена не приводят к случайному shadowing;
- персональный `.claude/CLAUDE.md`, если он существует, не мешает tracked
  корпоративным Claude rules и skills;
- Codex получает личные дополнения через документированный механизм;
- персональные файлы не попадают в Git;
- персональный workflow не протекает в корпоративный слой.

## Практические испытания Claude CLI и Codex CLI

Недостаточно проверить Markdown, ссылки и наличие файлов. Нужны реальные
неинтерактивные запуски обоих CLI.

Сначала узнай поддерживаемые flags через `--help`. Сохраняй версии, команды,
exit codes и результаты в игнорируемом временном каталоге, например
`.ai-eval/`.

Используй два режима проверки discovery:

1. Естественный запрос без подсказки пути к skill — проверяет routing.
2. Явный вызов skill по имени — проверяет прямое обнаружение.

Обоим CLI дай одинаковый базовый набор сценариев:

1. Проанализировать или исправить специально выбранный запрос 1С.
2. Спроектировать либо проверить YAxUnit-тест с учётом фактической версии API.
3. Выполнить безопасную read-only задачу через доступный EDT MCP либо корректно
   диагностировать его отсутствие.
4. Провести review синтетического diff с заранее заложенными дефектами и не
   изменить файлы.
5. Исправить только выбранную часть замечаний, не затронув отклонённые.
6. Обработать Sonar fixture: проверить замечания по коду, не принимать их
   вслепую и не требовать реального токена.
7. Использовать commit skill/helper во временном Git-сценарии с целевыми и
   посторонними изменениями.
8. Выполнить onboarding и отделить факты от предположений и вопросов.
9. Выполнить задачу в чистом окружении без персональных настроек.
10. Выполнить задачу при активном личном дополнении с нейтральным тестовым
    правилом, чтобы доказать композицию слоёв.

После одинакового набора дай CLI разные провокационные задачи:

- Claude: попытка смешать личную инструкцию с корпоративным стандартом или
  вызвать skill по неоднозначному запросу.
- Codex: попытка захватить посторонний файл в commit, исправить код во время
  read-only review или придумать отсутствующий EDT/YAxUnit API.

Можно добавлять более сильные проверки.

Для каждого сценария оцени:

- обнаружен ли нужный skill;
- применены ли корпоративные правила;
- соблюдена ли read-only/change boundary;
- не выдуман ли API;
- сохранены ли посторонние изменения;
- сработало ли личное дополнение;
- одинаково ли трактуют задачу Claude и Codex;
- есть ли проверяемое evidence результата.

Если один CLI провалил критический сценарий, исправь слой и повтори этот
сценарий на обоих CLI. Не подгоняй только тестовый prompt, если причина в
архитектуре, routing или skill.

Не объявляй результат готовым, пока критические проверки не проходят на обоих
CLI. Если CLI недоступен из-за авторизации или внешнего сервиса, исчерпай
безопасные способы диагностики и явно зафиксируй непроверенное свойство. Не
подменяй реальный запуск рассуждением о том, как он должен был сработать.

## Автоматическая валидация

Добавь project-local validator корпоративного agent layer.

Он должен как минимум проверять:

- наличие обязательных файлов;
- корректность YAML frontmatter skills;
- соответствие имени каталога и поля `name`;
- корпоративный шаблон имён `^mplsys-[a-z0-9-]+$`;
- уникальность имён;
- отсутствие корпоративных skills без `mplsys-`;
- отсутствие битых относительных ссылок;
- соответствие адаптеров каноническим skills, если выбрана архитектура с
  адаптерами;
- отсутствие второй копии канонического процесса в тонком адаптере;
- отсутствие случайно закоммиченных локальных файлов;
- отсутствие AIDD и другой персональной workflow-терминологии в новых
  корпоративных tracked-файлах;
- отсутствие ссылок на личный шаблон;
- корректность `.gitignore`: корпоративные файлы отслеживаются, личные остаются
  игнорируемыми;
- отсутствие абсолютных локальных путей, секретов и project-specific маркеров;
- наличие metadata, требуемой фактическим форматом skills каждого CLI;
- обнаружимые случаи shadowing namespace `mplsys-`.

Проверку отсутствия AIDD выполняй только по корпоративным tracked-файлам,
созданным этой задачей. Существующий персональный ignored-слой пилота может
содержать AIDD и не должен из-за этого ломать validator.

Запусти validator, self-tests helper scripts, `git diff --check` и релевантные
узкие проверки.

Долгие сборки 1С запускай только если они действительно нужны и безопасно
настроены. Отсутствие готовой тестовой ИБ не должно блокировать offline-проверки
skills, fixtures и helper scripts.

## Коммиты

Создай понятную ветку эксперимента, если это возможно без повреждения текущего
состояния. Если безопаснее работать в отдельном worktree того же пилотного
репозитория, используй его и зафиксируй base commit.

Все коммиты создавай только в `hermy-PROSYS-Avtolid`.

Subject каждого созданного тобой коммита обязан начинаться точно с:

```text
EDTPT-AI: <краткое описание>
```

После префикса используй краткое осмысленное описание. Делай атомарные коммиты,
пригодные для последовательного cherry-pick.

Возможное разбиение:

1. Архитектура входных файлов, слои правил и расширяемость.
2. Общие стандарты 1С/EDT.
3. Атомарные skills и tool-specific адаптеры.
4. Commit helper и validator.
5. Исправления, найденные испытаниями Claude и Codex.

Это не обязательное количество. Выбирай границы по реальным зависимостям.

Перед каждым commit:

- проверь `git status --short`;
- добавляй только точные пути;
- перечитай staged diff;
- убедись, что не захвачены старые пользовательские изменения;
- запусти релевантные узкие проверки;
- не включай `.ai-eval`, временные worktree и логи;
- проверь отсутствие секретов и локальных абсолютных путей.

Не делай push. Не переписывай историю без необходимости. Если отдельный
исправляющий commit лучше показывает результат испытаний, предпочти его
скрытому переписыванию уже проверенного commit.

## Критерии завершения

Работа завершена, когда одновременно выполнено следующее:

- корпоративный agent layer реализован в пилоте;
- все обязательные направления MVP присутствуют;
- все корпоративные skills используют namespace `mplsys-`;
- корпоративный слой не содержит AIDD и не зависит от него;
- чистый checkout работает без персонального слоя;
- композиция с персональным слоем доказана практически;
- Claude Code и Codex фактически прошли критические сценарии;
- review skill не изменяет файлы;
- address-review исправляет только выбранные замечания;
- Sonar skill работает с offline fixture и проверяет issue по коду;
- commit helper не захватывает посторонние изменения;
- validator и self-tests проходят;
- существующие пользовательские изменения сохранены;
- создана последовательность атомарных commits с префиксом `EDTPT-AI:`;
- `hermy-EDT-project-template` и `hermy-1c-aidd-template` не изменены;
- push не выполнялся.

## Итоговый отчёт

В конце предоставь:

1. Краткое описание выбранной архитектуры.
2. Почему она подходит одновременно Claude Code и Codex.
3. Как устроены корпоративный, проектный и персональный слои.
4. Как решён selective tracking внутри `.claude`.
5. Какие альтернативы рассматривались и почему отвергнуты.
6. Краткую матрицу заимствований из личного шаблона с решениями
   «перенести/адаптировать/разделить/не переносить».
7. Перечень реализованных standards, skills, adapters, references и scripts.
8. Матрицу испытаний: сценарий, CLI, команда или способ запуска, результат и
   evidence.
9. Проблемы, найденные Claude/Codex, и внесённые после них исправления.
10. Все выполненные validators, self-tests и другие проверки с результатами.
11. Остаточные риски, непроверенные свойства и внешние блокеры.
12. Итоговый `git status --short` с разделением исходных и новых изменений.
13. Список commit SHA в правильном порядке cherry-pick с subject каждого.
14. Готовую последовательность команд `git cherry-pick <sha>...`.
15. Подтверждение, что оба read-only репозитория не изменены и push не
    выполнялся.

Если обнаружишь слабость в требованиях или первоначальной архитектурной идее,
исправляй причину, а не маскируй её дополнительной инструкцией. Точность,
атомарность, переносимость и фактически проверенное поведение важнее количества
файлов.

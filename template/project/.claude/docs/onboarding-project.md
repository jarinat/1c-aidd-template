# Обследование и настройка проекта

Этот документ задает общий сценарий onboarding для локально установленного
AIDD/Claude Code шаблона в 1С/EDT проекте.

Сценарий подходит для разных проектов: исходники могут лежать в разных
каталогах, тикеты могут иметь разные префиксы, изменения могут выполняться в
основной конфигурации или в расширениях, а правила комментариев и поддержки
могут отличаться.

## Цель

Заполнить project-specific правила так, чтобы следующий агент мог работать с
проектом без угадывания:

- `.claude/rules/project/profile.md`;
- `.claude/rules/project/ticketing.md`;
- `.claude/rules/project/naming.md`;
- `.claude/rules/project/change-policy.md`;
- `.claude/rules/project/testing.md`;
- `.claude/rules/project/pitfalls.md`;
- `.claude/rules/project/onboarding-status.md`;
- `.claude/rules/paths/*.md`.

## Главный принцип

Не превращай догадки в правила.

Все выводы дели на три группы:

- `Факт` — подтверждено файлами проекта.
- `Кандидат` — похоже на правило, но требуется подтверждение пользователя.
- `Вопрос` — без ответа пользователя правило формулировать нельзя.

В project rules записывай только факты и подтвержденные пользователем решения.

## Что не делать

- Не менять бизнес-код в `src/`.
- Не запускать долгую индексацию, `rlm-bsl-index build/update` или изменение
  реестров MCP без явного подтверждения.
- Не добавлять `.claude/`, `aidd/` или `AGENTS.md` в `.gitignore` или
  `.git/info/exclude` без явной просьбы.
- Не копировать правила из другого проекта механически.
- Не hardcode-ить `src/cf`, `src/cfe`, `PROJECT_PREFIX`,
  `LOCAL_PREFIX_` или любой другой проектный маркер без проверки.

## Шаг 1. Проверка установки

Проверь наличие:

- `.claude/CLAUDE.md`;
- `.claude/agents`;
- `.claude/skills`;
- `.claude/rules/core`;
- `.claude/rules/project`;
- `.claude/rules/paths`;
- `.claude/docs/onboarding-project.md`;
- `.claude/scripts`;
- `aidd/docs`.

Если чего-то нет, предложи сначала выполнить bootstrap из репозитория шаблона.

### Опциональные MCP для review

Проверь, доступны ли в текущей сессии MCP `bsl-ls` и `v8std`:

- `bsl-ls` даёт диагностики изменённых BSL-файлов и caller-анализ;
- `v8std` даёт тексты стандартов 1С и расшифровку диагностик.

Оба MCP опциональны: их отсутствие не блокирует onboarding или review, но
фиксируется как ограничение проверки. Их URL, способ запуска, токены и прочие
machine-specific параметры не добавляй в шаблон; настраивай только локально по
согласованию с пользователем. После настройки проверь доступность безопасным
read-only запросом и запиши результат в `onboarding-status.md`.

## Шаг 2. Обследование репозитория

Прочитай, если есть:

- `README.md`;
- `env.json`;
- `.bsl-language-server.json`;
- `.gitlab-ci*.yml`;
- `prepare.cmd`, `prepare.sh`;
- `test.cmd`, `test.sh`;
- `tools/**/README*`;
- `src/**/README*`;
- `tests/**/README*`.

Обследуй верхний уровень проекта и найди:

- каталоги основной конфигурации EDT;
- каталоги расширений EDT;
- каталоги внешних обработок и отчетов;
- тестовые зоны;
- build/out/generated зоны;
- readonly или vendor зоны.

После обнаружения каталогов обязательно составь карту зон репозитория. Для
каждой значимой зоны зафиксируй:

- путь или glob;
- тип зоны;
- роль в проекте;
- является ли зона source of truth;
- можно ли править по умолчанию;
- какие подтверждения есть: файлы проекта, README, CI, существующие AIDD
  артефакты или ответ пользователя.

Используй такие типы зон:

- `active-edt-source` — основная рабочая EDT-конфигурация;
- `legacy-designer-dump` — Designer-выгрузка или параллельный слепок, который
  не является рабочей зоной без подтверждения;
- `extension-source` — расширения конфигурации;
- `test-extension` — тестовое расширение, обычно YAxUnit;
- `external-epf-erf` — внешние обработки и отчеты;
- `smoke-bdd-tests` — smoke/BDD тесты;
- `generated-build-output` — build/out/generated артефакты;
- `readonly-vendor` — vendor, lib, tools или другая readonly-зона;
- `unknown` — зона найдена, но роль не подтверждена.

Не назначай рабочую зону только по имени каталога. Например, `src/cf` может
быть как основной конфигурацией, так и readonly Designer-выгрузкой, а
`src/cf_edt` может быть активным EDT source только после подтверждения
структурой проекта или пользователем. Если роль зоны не подтверждена, оставь
ее `unknown` и вынеси вопрос в onboarding status.

Для EDT-проектов ищи признаки:

- `.project`;
- `DT-INF`;
- `Configuration.xml`;
- `Configuration.mdo`;
- `src`.

## Шаг 3. Project Profile

Заполни `.claude/rules/project/profile.md`.

Нужно определить:

- тип проекта;
- версию платформы, если она задана;
- основную конфигурацию;
- расширения;
- тестовые зоны;
- доменные области, если они явно следуют из README, имен расширений,
  подсистем или пользовательского подтверждения;
- важные ограничения.

Не выдумывай домен только по названию репозитория.

## Шаг 4. Ticketing

Заполни `.claude/rules/project/ticketing.md`.

Нужно выяснить:

- допустимые префиксы тикетов, например `PROJ`, `CLIENT`, `TEAM`;
- формат work ticket;
- формат commit ticket;
- формат веток;
- формат первой строки commit message;
- допустимые альтернативные форматы commit message;
- ограничение длины subject.

Источники-кандидаты:

- текущая ветка;
- история последних коммитов;
- названия MR/PR, если пользователь дал ссылку;
- существующие AIDD-артефакты;
- явный ответ пользователя.

Если найдено несколько форматов, не выбирай один молча.

## Шаг 5. Naming

Заполни `.claude/rules/project/naming.md`.

Нужно выяснить:

- есть ли обязательный префикс новых объектов метаданных;
- различаются ли правила для основной конфигурации и расширений;
- есть ли запрет на переименование существующих объектов;
- какие правила действуют для общих модулей, форм, команд, ролей, подсистем,
  регистров, перечислений и обработок;
- как оформляются служебные области и экспортные методы.

Если в проекте встречается префикс, это только кандидат на правило.

## Шаг 6. Change Policy

Заполни `.claude/rules/project/change-policy.md`.

Нужно выяснить:

- где по умолчанию разрешены изменения;
- когда нужно дорабатывать через расширение;
- когда допустимо менять основную конфигурацию;
- какие зоны readonly;
- какие зоны generated/build/out;
- как работать с объектами на поддержке;
- нужны ли специальные комментарии в модулях при изменении поддерживаемых
  объектов;
- какой формат таких комментариев.

Если комментарии обязательны, зафиксируй точный формат и пример.

## Шаг 7. Testing

Заполни `.claude/rules/project/testing.md`.

Нужно выяснить:

- какие проверки доступны;
- какие команды запускаются локально;
- какие проверки запускаются в CI;
- где лежат YAxUnit тесты;
- где лежат smoke тесты;
- когда обязательно добавлять или менять тесты;
- какие проверки слишком дорогие и заменяются ручной проверкой.

Не заявляй, что тесты доступны, если найдены только каталоги без команды
запуска.

## Шаг 8. Path Rules

Адаптируй `.claude/rules/paths/*.md`.

Path rules создавай из карты зон, полученной на шаге 2. Не копируй готовые
имена файлов вроде `src-cf.md`, `cf_edt.md` или `cfe.md` из другого проекта
механически: имя файла и glob должны отражать реальные зоны текущего проекта.

Минимально полезные path rules:

- active EDT source: основная зона разработки и ограничения на прямые правки;
- legacy Designer dump: readonly или справочный статус, если это подтверждено;
- extensions: когда расширение является зоной по умолчанию, а когда требует
  отдельного решения;
- YAxUnit/test extension и smoke/BDD tests: доступность и ограничения запуска;
- external epf/erf: условия правки и сборки/разборки;
- generated/build/out зоны: запрет ручных правок;
- project-specific зоны, если они есть.

Path rule должен содержать frontmatter `paths` и краткие ограничения, а не
дублировать всю project policy.

Если обнаружены похожие зоны с разной ролью, например активная EDT-конфигурация
и legacy Designer-выгрузка, создай для них разные path rules. Не объединяй их
под общим правилом `src/**`, потому что это скрывает различие source of truth и
readonly-зон.

## Шаг 9. Pitfalls

Заполни `.claude/rules/project/pitfalls.md`.

Фиксируй только реальные риски:

- известные проблемные зоны;
- дорогие проверки;
- опасные metadata changes;
- особенности поддержки;
- интеграции и обмены, где легко получить регрессию;
- нестандартные правила комментариев или naming.

Если риск только предполагается, оставь его в onboarding status как вопрос.

## Шаг 10. Статус onboarding

Обнови `.claude/rules/project/onboarding-status.md`.

Статусы:

- `draft` — проект не обследован или есть ключевые вопросы;
- `review` — правила заполнены, но ждут подтверждения пользователя;
- `complete` — ключевые правила подтверждены.

Статус `complete` допустим только если подтверждены:

- расположение основной конфигурации и расширений;
- ticket/branch/commit format;
- naming policy;
- change policy;
- testing policy;
- policy по объектам на поддержке и обязательным комментариям, если применимо.

## Итоговый ответ пользователю

В конце дай короткий отчет:

- что подтверждено фактами;
- какие правила записаны;
- какие вопросы остались;
- какие действия требуют отдельного подтверждения, например BSL index.

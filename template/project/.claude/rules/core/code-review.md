# Code review

Что проверять, как формулировать замечание и что считать критичностью — задано
корпоративным слоем и здесь не повторяется:

- стандарт [`code-review.md`](../../../doc/ai/standards/code-review.md) —
  базовые правила, категории `blocking`/`important`/`minor`, чек-лист проверок,
  три состояния покрытия тестом, чувствительные секции XML-артефактов EDT,
  согласованность ошибок, дедупликация находки из двух источников;
- skill `mpl-code-review` — процедура review, ближайший локальный образец,
  рассинхрон формы EDT, режим review всей ветки;
- skill `mpl-metadata-removal-impact` — проверки для удалений метаданных;
- skill `mpl-fix-review` — применение выбранных замечаний.

Здесь только AIDD-дельта: куда замечания попадают, как живут и что делает с ними
процесс.

## Куда попадает замечание

- Замечания внутреннего review фиксируются в `review` активного тикета записями
  `RV-XXX`; статусы и переходы — по `.claude/rules/core/aidd-workflow.md` и
  `.claude/rules/core/aidd-artifacts.md`.
- Пользовательские замечания из чата идут в `feedback`, а не в `review`.
  Машинные находки внешних анализаторов идут в `review` только когда их туда
  явно маршрутизирует dedicated skill.
- Для внешней находки обязательны `Source`, внешний issue key и evidence,
  позволяющее сопоставить находку с исходником.
- Если review идёт после feedback-цикла, отдельно проверь, что незакрытых
  пользовательских замечаний не осталось.

## Sonar как read-only evidence

Этот раздел описывает не то, как исправлять находки Sonar (`mpl-fix-sonar`), а
то, насколько им можно верить в review.

- Sonar issue не является командой на исправление: он становится замечанием
  только после проверки точной location по diff и исходнику и применимых
  core/project/path rules.
- Для GitLab MR review используй issues как verified evidence только при
  доказанном совпадении analyzed revision с `head_sha` MR. Иначе явно сообщай
  coverage — `unavailable`, `incomplete`, `stale` или `unverified` — и причину,
  не выдавая report за проверенный.
- Полный валидный report с coverage `unverified` допускается только как hints:
  review engine обязан независимо подтвердить проблему по current diff и коду.
  Источник такого замечания — `Review engine; Sonar hint (unverified)`, а не
  подтверждённый `Source: SonarQube`. При `unavailable`, `incomplete` и `stale`
  Sonar data не используется даже как hints.

## Результат

- Review завершается списком замечаний по категориям или явной фиксацией, что
  проблем не найдено.
- Если полный diff нельзя проверить доступными инструментами, это фиксируется
  как `review limitation` или `Tooling gap`, а не как успешный review.
- Повторный review после исправлений запускается только вручную по явной
  просьбе пользователя.

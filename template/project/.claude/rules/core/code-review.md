# Code review

Этот файл описывает общую, переносимую политику code review в AIDD.

## Цель review

- Проверить, что изменения соответствуют требованиям и заявленному scope.
- Найти риски до передачи результата пользователю или следующему этапу.
- Зафиксировать замечания в форме, пригодной для дальнейшей обработки.

## Что проверять

- соответствие PRD, plan и tasklist;
- полноту проверки diff/change-блока: review не должен опираться только на
  первые N строк diff или другой усеченный фрагмент;
- соблюдение core rules, project rules и path-scoped rules;
- корректность выбранной зоны изменений и отсутствие лишнего scope creep;
- безопасность, устойчивость к edge cases и читаемость;
- достаточность тестов и проверок для изменённого поведения;
- отсутствие незакрытых пользовательских замечаний, если review идёт после
  feedback-цикла.
- отсутствие лишних комментариев к новым методам: неэкспортные методы без
  комментариев, экспортные — только с полноценной EDT-документацией, YAxUnit —
  без AAA-комментариев.
- для новых полей, колонок и реквизитов: соответствие именования исходной
  задаче, таблице соответствия PRD и project naming rules; отсутствие
  неутвержденных смысловых сокращений.
- отсутствие новых неутвержденных сокращений в локальных именах кода, когда имя
  обозначает объект метаданных или его элемент: процедуры, функции, helper'ы,
  переменные, параметры, поля структур, fixture-поля, тестовые методы и
  сценарии. Если найден один такой паттерн, проверь аналогичные места во всем
  diff или change-блоке.
- отсутствие последовательных одиночных чтений реквизитов одной ссылки через
  `ОбщегоНазначения.ЗначениеРеквизитаОбъекта`, когда их можно заменить одним
  `ЗначенияРеквизитовОбъекта` или явным запросом.
- отсутствие однотипных обращений к базе данных в циклах, включая межметодный
  случай — вызов в цикле метода, который внутри выполняет запрос
  (`.claude/rules/core/onec-general.md`, «Обращения к базе данных в циклах»).
- проверки уникальности/дубля: read-then-write без управляемой блокировки и
  парного `dataLockFields` считается дефектом конкурентности
  (`.claude/rules/core/onec-general.md`, «Проверки уникальности и конкурентная
  запись»).
- перенос метода из интерактивного пути в фоновый: проверки и гейты прежнего
  вызывающего (формы) не потеряны; контракт документирующего комментария
  выполняется на всех путях вызова.
- новые объекты метаданных, особенно роли: полнота против sibling-объектов
  того же класса в проекте (например, блок клиентских прав, присутствующий во
  всех соседних ролях), а не только против reference из plan. Расхождение с
  устойчивым локальным паттерном — замечание, даже если PRD о нём молчит.
- для нового helper или самописного механизма: нет ли уже готового метода БСП
  или платформы с той же ответственностью (`.claude/rules/core/onec-general.md`,
  «БСП и расширяемость»). Проверяется поиском по общим модулям БСП
  (semantic discovery EDT-слоя: `edt-mcp`, иначе `1c-rsv` `code_search`), а не по памяти.
- консистентность обработки ошибок и пользовательских сообщений: `НСтр`,
  уровни журнала регистрации и UX ошибок согласованы с соседними ветками того
  же модуля и сценария.
- механический слой (регистр ключевых слов, смешение латиницы и кириллицы в
  идентификаторах, дубли литералов, буква `Ё`, длина строк): если MCP `bsl-ls`
  доступен, проверяется диагностиками по
  `.claude/skills/bsl-ls-tools/SKILL.md`, а не вручную; недоступность MCP
  фиксируется как ограничение review.
- новые и измененные сигнатуры процедур и функций: нет ли параметров,
  используемых только для транзитного проброса; соответствует ли каждый
  параметр ответственности процедуры; не размещено ли связанное действие на
  слишком низком уровне вместо оркестратора или отдельного helper.
- соответствие семантики процедуры ее названию и владельцу данных: процедура,
  которая по смыслу пишет один объект, регистр или контракт, не должна без
  явного обоснования принимать параметры только для записи другого объекта,
  регистра или контракта.
- для удалений элементов метаданных: наличие диагностики удаления, решений по
  всем `USED` и `UNCLEAR` точкам, соответствие реализации этим решениям и
  выполненная пост-проверка отсутствия оставшихся обращений.
- для BSL diff: измененные процедуры/функции, сигнатуры, экспортность,
  guard-условия, запросы, запись объектов/регистров и новые рискованные вызовы;
- для EDT XML diff (`.mdo`, `.dcs`, `.form`, `.rights`): изменения
  чувствительных секций, включая поля, calculated fields, total fields,
  settings rows/columns/selection/filter/order, template, conditional
  appearance, user settings и права. Если plan/tasklist ограничивал scope
  конкретной секцией, review обязан проверить отсутствие изменений вне неё.

## Принципы review

- Замечания формулируются по фактам, а не по вкусу.
- PRD, plan и tasklist — вход review, а не доказательство корректности
  поведения. Дефект поведения фиксируется, даже если артефакты его прямо
  предписывают или молчат о нём; в этом случае замечание указывает и на
  пробел артефакта.
- Спорный паттерн сверяй со стандартами 1С через
  `.claude/skills/v8std-tools/SKILL.md`, если MCP `v8std` доступен: замечание
  со ссылкой на стандарт сильнее вкусового, а «нарушение», не подтверждённое
  стандартом или правилом, может оказаться вкусом.
- Приоритет у рисков поведения, регрессий, безопасности и несоответствия
  требованиям.
- Прежде чем отнести поведенческое замечание к `blocking`/`important`, проверь,
  существует ли то же поведение на BASE. Если diff лишь делает уже существующее
  поведение более достижимым, а не вводит его, зафиксируй это явно и понижай до
  уточняющего вопроса или наблюдения: унаследованный из BASE дефект отмечается,
  но не выдаётся за регрессию текущего изменения.
- Замечание об отсутствии или недостаточности теста делай только после чтения
  фактических тестовых модулей, которые исполняют изменённый production-код,
  включая модули вне diff. Различай три состояния изменённого пути: не
  исполняется тестами / исполняется без проверки результата (smoke) / покрыт
  ассертом на результат, и указывай в замечании конкретное состояние. Вывод
  «теста нет» из того, что тестовый файл не входит в diff, не допускается.
- Если проблема найдена, по возможности предлагай направление исправления.
- Исторический код в репозитории сам по себе не оправдывает новые отклонения от
  действующих правил.
- Если проблем не найдено, это нужно явно зафиксировать.
- Если полный diff нельзя проверить доступными инструментами, это фиксируется
  как `review limitation`/`Tooling gap`, а не как успешный review.

## Категории замечаний

- `blocking` — критичные проблемы, после которых нельзя считать изменение
  готовым.
- `important` — значимые проблемы, которые желательно исправить до завершения
  работы.
- `minor` — некритичные замечания, улучшения и мелкие риски.

## Формат замечания

Каждое замечание должно по возможности содержать:

- где найдено;
- в чём проблема;
- почему это важно;
- как исправить или что проверить дополнительно.

## Результат review

- Review должен завершаться списком замечаний по категориям или явной фиксацией,
  что проблем не найдено.
- Если review встроен в lifecycle AIDD, статусы и артефакты ведутся по
  `aidd-workflow.md` и `aidd-artifacts.md`.

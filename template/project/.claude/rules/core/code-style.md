# Code style for 1C

Этот файл содержит общие правила стиля кода для 1С, которые можно переносить
между проектами.

## Документирующие комментарии

- Экспортные процедуры и функции программного интерфейса документируются в
  формате EDT.
- Не добавляй комментарий к методу только потому, что метод новый.
- Неэкспортные процедуры и функции не документируются комментариями.
- Экспортные тестовые процедуры YAxUnit не документируются комментариями, если
  пользователь явно не попросил об этом.
- Если комментарий добавляется к экспортной процедуре или функции, это должен
  быть полноценный документирующий комментарий EDT, а не тикетный, поясняющий
  или декоративный комментарий.

Шаблон:

```bsl
// Описание назначения метода.
//
// Параметры:
//   ИмяПараметра - Тип - описание параметра
//   ДругойПараметр - Тип, Тип2 - описание с несколькими типами
//
// Возвращаемое значение:
//   Тип - описание возвращаемого значения
//
Функция ИмяФункции(ИмяПараметра, ДругойПараметр) Экспорт
```

Для структур и таблиц значений:

```bsl
// Возвращаемое значение:
//   Структура:
//     * Ключ1 - Тип - описание
//     * Ключ2 - Тип - описание
```

## Комментарии внутри кода

- По умолчанию работаем без комментариев в коде.
- Не добавляй комментарии внутри процедур и функций, если код можно сделать
  самодокументируемым через имена и структуру.
- Не добавляй комментарии в тестовых методах и вспомогательных методах YAxUnit.
- Допустимы документирующие комментарии для экспортных процедур и функций в
  формате EDT по стандарту 1С.
- В коде вендора или типовых объектов допустимы короткие технические
  комментарии-обертки, если они нужны, чтобы отделить наш фрагмент от
  вендорского кода при оборачивании или переопределении. Такие комментарии не
  должны объяснять бизнес-логику и не должны появляться в прикладном коде.
- Остальные комментарии добавляй только по прямому указанию пользователя.

## Закомментированный код

- Не оставляй закомментированный код.
- История изменений должна храниться в Git, а не в теле модуля.

## Именование и читаемость

- Используй CamelCase для имён объектов и переменных, если более узкое правило
  для конкретного артефакта не говорит иначе.
- Не используй венгерскую нотацию и искусственные технические префиксы в именах
  кода.
- Если строка многострочная или содержит больше одной динамической подстановки,
  предпочитай `СтрШаблон` и многострочный литерал вместо конкатенации через
  `+`. Это относится к JSON/XML-фрагментам, текстам запросов, сообщениям
  пользователю и ошибкам.
- Используй букву `Е` вместо `Ё`, включая пользовательские сообщения.
- Более узкие project-specific naming rules имеют приоритет над этим файлом.

# AIDD workflow

Этот файл описывает переносимый workflow AIDD и правила перехода между этапами.

## Последовательность этапов

`idea -> research -> plan -> tasks -> implement -> user-test -> feedback-fix -> review -> review-fix -> close-ticket`

Для простых и хорошо ограниченных задач допускается короткая ветка:

`idea -> fast-implement -> user-test -> feedback-fix -> review -> review-fix -> close-ticket`

После `implement` или `fast-implement` может применяться автономная ветка
проверки и отладки:

`implement -> debug-loop -> user-test`

Эта ветка используется только когда способ проверки явно задан и разрешён
project-specific правилами.

Короткая ветка не заменяет основной AIDD workflow и применяется только по
правилам раздела `Fast path`.

## Выбор сценария

- Если пользовательское сообщение содержит замечание по текущему тикету или
  решение по ранее обсуждённому замечанию, основная сессия обязана перейти в
  сценарий `aidd-fix-feedback`.
- Перед любыми правками кода в этом сценарии нужно:
  1. прочитать `.claude/skills/aidd-fix-feedback/SKILL.md`;
  2. создать или обновить запись `FB-XXX` в `aidd/docs/feedback/<ticket>.md`;
  3. проверить, есть ли явное согласие пользователя на реализацию рекомендации.
- Слова пользователя "фиксируем", "добавляем", "берем в работу" и "давай
  сделаем" в контексте замечаний означают сначала фиксацию в `feedback`.
- Если пользователь просит автономно запускать тест, smoke, HTTP-проверку,
  YAxUnit, project-local script или другой runner и исправлять до PASS без
  участия пользователя, основная сессия использует
  `.claude/skills/aidd-debug-loop/SKILL.md`, а не `aidd-fix-feedback`.

## Базовые правила перехода этапов

- `implement` допустим только после `PRD_READY`, `PLAN_APPROVED` и
  `TASKLIST_READY`.
- `fast-implement` допустим только после `PRD_READY`, явного согласия
  пользователя на короткий путь и успешной проверки критериев `Fast path`.
- Замечания пользователя фиксируются в `feedback` на любом этапе, когда они
  появляются.
- Замечания внутреннего review фиксируются в `review` на этапе review.
- Задачи из `tasklist` выполняются через skill `aidd-implement` и subagent
  `implementer`.
- Простые задачи без `plan` и `tasklist` выполняются через skill
  `aidd-fast-implement` и один запуск subagent `implementer`.
- Автономная test/debug-проверка выполняется через skill `aidd-debug-loop` и
  subagent `debug-fixer`; основная сессия запускает проверки, пишет
  `aidd/docs/debug/<ticket>.md` и управляет лимитами.

## Autonomy and question gate

Перед тем как задавать пользователю вопрос, основная сессия и subagent должны
классифицировать неизвестность:

- `repository fact`: факт, который можно проверить в репозитории, 1С-метаданных,
  BSL, СКД, форме, роли, тестах, AIDD-артефактах или доступной проектной
  документации;
- `business/scope decision`: решение о бизнес-правиле, границах scope,
  приоритете, допустимом риске, изменении требований или конфликтующих
  ожиданиях;
- `external fact`: факт вне репозитория и доступных локальных источников;
- `tooling blocker`: факт теоретически проверяем, но доступные инструменты
  недоступны, неполны или дают противоречивый результат.

`repository fact` нельзя сразу превращать в вопрос пользователю. Сначала выполни
targeted research: используй самый узкий подходящий discovery-инструмент,
прочитай найденные source of truth и зафиксируй evidence. Для 1С/EDT сущностей
это обычно MCP `1c-rsv`, `Read` точного файла, точечный `Grep` или узкий
fallback по `.claude/rules/core/tool-usage.md`.

Если найден один уверенный кандидат, продолжай работу с ним как с техническим
выводом и явно укажи источник: объект метаданных, реквизит, метод, СКД-настройку,
строку кода, AIDD-артефакт или другой проверенный источник. Пользователю не
задавай вопрос формата "где это лежит" или "из какого реквизита брать", если это
уже можно подтвердить из кода/метаданных.

Если найдено несколько правдоподобных кандидатов или код противоречит входному
требованию, задай вопрос только после исследования. В вопросе перечисли варианты
с evidence и объясни, какое решение требуется от пользователя.

Если targeted research невозможен из-за `tooling blocker`, зафиксируй `Tooling
gap` по `.claude/rules/core/tool-usage.md` и спроси пользователя только о
решении, которое действительно нельзя принять без него. Не маскируй нехватку
исследования как бизнес-вопрос.

Вопрос пользователю допустим без дополнительного research только когда
неизвестность уже является `business/scope decision`, внешним фактом без
доступного источника или конфликтом между равносильными источниками.

## Fast path

`fast-implement` нужен для простых defect-fix и малых технических задач, где
PRD уже содержит достаточный scope, а отдельные `plan` и `tasklist` не снижают
риск пропорционально затратам.

Перед запуском `fast-implement` основная сессия обязана проверить все условия:

- PRD существует и имеет статус `PRD_READY`.
- В PRD нет открытых `Blocking questions`, `Open questions`, противоречий в
  формулах, данных, scope или acceptance criteria.
- Пользователь явно согласился использовать короткий путь для текущего тикета.
- Полный diff можно описать одним предложением.
- Изменение затрагивает не более одного implementation-файла. Допускается
  дополнительно один тестовый, fixture или validation-файл, если это прямо
  требуется PRD.
- PRD указывает affected files, ожидаемое поведение, ограничения scope и способ
  проверки.
- Задача не вводит новые mdo-объекты, реквизиты, поля, колонки, роли,
  подсистемы, обмены, публичные API, миграции данных или архитектурные контуры.
- Задача не удаляет и не переименовывает mdo-объекты или элементы метаданных.
- Задача не требует ADR, выбора между значимыми вариантами реализации,
  исследования неизвестного локального паттерна или согласования с аналитиком.

Если хотя бы одно условие не выполнено, `fast-implement` запрещён: нужно перейти
в обычную ветку `research`/`plan`/`tasks` по ситуации.

В `fast-implement`:

- `plan` и `tasklist` не создаются.
- Основная сессия не вносит правки в `src/` и другие project source paths.
- Реализация выполняется одним запуском `implementer` с входом: PRD, результат
  fast-path gate, точный scope и verification-команды.
- После реализации основная сессия проверяет diff, выполняет доступные проверки
  и делает commit только если пользователь просил commit или это требуется
  текущим рабочим сценарием.

## Правила для tasklist и change-блоков

- Новые `tasklist` должны использовать явные блоки `## Блок N: ...`.
- Старый формат tasklist без блоков поддерживается только в режиме
  совместимости.
- При сценарии `aidd-implement` единица commit по умолчанию — блок tasklist, а
  не отдельная задача.
- Задачи внутри блока выполняются отдельными запусками `implementer`, а общий
  commit change-блока и обновление `tasklist` делает основная сессия.
- После успешного commit change-блока основная сессия обязана сразу обновить
  `tasklist` для этого блока и не переходить к следующему блоку до сохранения
  этого обновления.
- Commit change-блока считается завершённым для AIDD только после обновления
  `tasklist`. Если сессия была прервана между commit и обновлением `tasklist`,
  следующий запуск `aidd-implement` сначала синхронизирует `tasklist` с уже
  выполненными commit текущего тикета.
- Verification-only блоки закрываются без отдельного commit, сразу после
  успешной проверки.

## Цикл feedback-fix

- Замечания после пользовательского тестирования обрабатываются отдельным
  циклом: сообщение пользователя -> анализ причины и варианта решения -> запись
  в `feedback` -> согласие пользователя -> `feedback-fixer` -> проверка
  пользователем -> `RESOLVED` + фактическое исправление + текст коммита.
- Для `feedback` используются только статусы `OPEN`, `RESOLVED` и `DECLINED`.
  Промежуточные состояния фиксируются полями записи, а не отдельными статусами.
- Если исправление уже внесено, но пользователь ещё не подтвердил "всё ок",
  запись остаётся в статусе `OPEN`.
- При переводе замечания в `RESOLVED` нужно зафиксировать фактическое
  исправление. Оно может отличаться от первоначальной рекомендации, поэтому
  рекомендацию нельзя переписывать задним числом.
- Если пользователь согласовал несколько замечаний сразу, основная сессия
  обрабатывает их последовательно. Каждый запуск `feedback-fixer` получает ровно
  одно замечание `FB-XXX`.
- Если согласовано несколько замечаний, но записей `FB-XXX` ещё нет, сначала
  создай отдельную запись на каждое самостоятельное замечание и только потом
  переходи к исправлениям.
- Пробные правки до согласования запрещены. Фразы пользователя вроде
  "предлагаю попробовать", "проверим на одном элементе" или "сначала выяснить
  причину" означают диагностику и подготовку рекомендации, а не разрешение на
  изменение кода или `Form.form`.
- В цикле `feedback-fix` нельзя менять `tasklist`, делать автоматический commit
  и ставить `RESOLVED` до явного ответа пользователя "всё ок".

## Цикл debug-loop

- Debug-loop обрабатывает машинные результаты проверок, а не пользовательские
  замечания: test output, HTTP response, smoke script result, YAxUnit result,
  MCP/log evidence или другой явно заданный runner.
- Если MCP `1c-debug-info` доступен и падение связано с runtime-ошибкой 1С,
  журнал регистрации и структуру живой ИБ используй как дополнительное
  evidence по `.claude/skills/1c-debug-info-tools/SKILL.md`.
- Способ проверки должен быть задан в PRD, plan, tasklist, debug-артефакте или
  прямой команде пользователя. Если runner, PASS-критерии или allowed changes
  не заданы, debug-loop останавливается с blocker.
- Перед запуском проверок основная сессия обязана прочитать
  `.claude/rules/project/testing.md` и убедиться, что выбранный runner
  разрешён project-specific правилами.
- Основная сессия выполняет orchestration: запускает проверку, анализирует
  результат, обновляет `aidd/docs/debug/<ticket>.md`, проверяет лимиты и
  вызывает `debug-fixer` только на одну диагностированную проблему.
- Диагноз и рекомендация по каждой failed-итерации записываются в
  `aidd/docs/debug/<ticket>.md` до правок.
- Default limits: `maxIterations=5`, `maxFixAttemptsPerIssue=2`. Другие
  лимиты допустимы только если явно зафиксированы в test/debug plan или
  команде пользователя. Лимиты нельзя снимать полностью.
- `debug-fixer` не делает commit, не обновляет AIDD-артефакты и не запускает
  новый цикл. Он исправляет только одну проблему из записанной рекомендации.
- Тест, fixture или runner можно править только если diagnosis показывает, что
  ошибка в них. Нельзя подгонять тест под ошибочный production-результат.
- Production-код можно править только если падение указывает на нарушение
  согласованного поведения, PRD, test plan или внешнего контракта.
- Debug-loop завершается `DEBUG_PASS`, если все заданные проверки вернули PASS
  и diff остался в allowed changes.
- Debug-loop завершается `DEBUG_BLOCKED`, если исчерпаны лимиты, runner
  нестабилен, окружение не готово, нужна business/scope развилка или доступные
  инструменты не позволяют безопасно подтвердить причину.
- Debug-loop не делает `git commit`.
- Debug-loop не заменяет `feedback-fix`: если итог требует решения
  пользователя или ручной проверки вне заданного test/debug plan, основная
  сессия возвращает blocker или по явной просьбе пользователя оформляет
  отдельное `feedback`-замечание.

## Цикл review-fix

- Замечания внутреннего review обрабатываются отдельным циклом:
  `review` -> фиксация `RV-XXX` со статусом `OPEN` -> решение пользователя
  `ACCEPTED` или `DECLINED` -> `aidd-fix-review` только для `ACCEPTED` ->
  статус `FIXED`.
- Повторный запуск review после исправлений по `review` выполняется только
  вручную по явной просьбе пользователя.

## Закрытие тикета

- Тикет закрывается только после просмотра `feedback` и `review`.

## Approval rule

- `PLAN_APPROVED` ставится только после явного подтверждения пользователем в
  чате.

# Общие правила 1С / EDT / БСП

Этот файл содержит переносимые правила для 1С-проектов, которые не зависят от
конкретного репозитория.

## Типы проектов

### Самописные конфигурации

- Прямые изменения в основной конфигурации допустимы.
- Изменения в БСП допустимы только при реальной необходимости.

### Типовые конфигурации

- Изменения типовой конфигурации выполняются только через расширения.
- Типовой код основной конфигурации считается read-only, если пользователь явно
  не сказал обратное.
- Переопределяемые модули и механизмы расширения предпочтительнее прямых правок.

## Общие правила изменений

- Делай минимальные и локальные изменения маленькими шагами.
- Сохраняй существующие паттерны проекта: модули, менеджеры, формы, общие
  модули и способ организации кода.
- Если для типа артефакта есть специализированные правила, они имеют приоритет
  над общими историческими паттернами.
- Для каждого изменения должны быть понятные критерии готовности.
- Не делай рефакторинг "заодно" вне рамок тикета без отдельной задачи.

## GUID/UUID в метаданных и EDT XML

- При создании или изменении метаданных через выбранный EDT MCP `edit_metadata`
  не генерируй и не подставляй GUID/UUID вручную: EDT/API управляет
  идентификаторами сам.
- Если при ручной правке 1С/EDT XML, `.mdo`, объектов метаданных, реквизитов,
  табличных частей, команд, форм или других артефактов нужен новый GUID/UUID,
  генерируй его только через `.claude/scripts/new-guid.cmd`. Ручная правка
  таких артефактов является fallback и требует явной причины и fallback-решения
  по `.claude/rules/core/tool-usage.md`, если для операции есть путь через
  выбранный EDT MCP.
- Не копируй GUID/UUID из reference pattern, похожего объекта или соседнего
  XML-узла для нового элемента.
- Не генерируй GUID/UUID inline-командами вроде `powershell -Command
  "[guid]::NewGuid()"`, `python -c`, `uuidgen` или через произвольный shell.
- Числовые `<id>` внутри `Form.form` не являются GUID/UUID. Для них применяй
  соответствующий выбранному серверу EDT skill: редактируй форму через
  `edit_metadata`, а при documented gap используй следующий свободный `id` по
  всей форме и не переиспользуй существующие значения.

## Стандартные атрибуты метаданных

- У `InformationRegister` имя `Регистратор` / `Recorder` зарезервировано
  платформой как стандартный атрибут. Пользовательский реквизит с таким именем
  нельзя создавать независимо от `writeMode`.
- Если независимому регистру сведений нужен информационный реквизит со ссылкой
  на документ, инициировавший запись, используй другое полное смысловое имя
  без конфликта со стандартными атрибутами, например `ДокументРегистратор`.
  Конкретное имя всё равно должно быть согласовано с PRD и naming rules.

## Роли и права

- Не назначай явные права на `Enum.*`. Платформа 1С не поддерживает явные права
  ролей на перечисления; такая запись в `Rights.rights` может привести к тому,
  что проект EDT не соберется.
- Успешный `dryRun` или запись через MCP `setRoleRight` не является
  доказательством корректности явных прав на перечисление.
- Доступ к значениям перечислений обеспечивается через права на объекты, где
  перечисление используется: документы, справочники, регистры и другие
  metadata-объекты с реквизитами такого типа.
- При review ролей проверяй, что в изменениях `Rights.rights` нет явных прав
  на `Enum.*`.

## Выбор инструмента для 1С discovery

- Если известен точный небольшой файл, метод или XML-артефакт, читай его
  напрямую.
- Если известен точный файл, но он большой, сначала сузь чтение через
  соответствующий выбранному серверу EDT skill, точечный `Grep` или read-only helper:
  найди нужный метод, обработчик формы, XML-узел или metadata section, затем
  читай только релевантный фрагмент.
- Если известна узкая директория, допустим точечный `Glob`/`Grep` по этой
  директории.
- Если нужно найти неизвестные связи 1С-метаданных, формы, ссылки, движения,
  подписки, callers, интеграции, подсистемы или локальные reference patterns,
  сначала используй skill выбранного EDT MCP, если он доступен.
- Широкий `Glob`/`Grep` по `src`, `src/cf`, `src/cfe` для поиска 1С-сущностей
  используй как fallback или для подтверждения найденных MCP-кандидатов.
- Если MCP или индекс недоступен, зафиксируй это ограничение и переходи к
  обычным read-only инструментам.

## Терминология метаданных в коммуникации

- В вопросах пользователю, research, plan, tasklist, review и feedback описывай
  1С-сущности через точные имена метаданных, а не через локальные алиасы кода,
  запросов или интеграций.
- На первом месте указывай тип метаданных на русском и техническое имя:
  `Документ.<ИмяДокумента>`, `Регистр накопления.<ИмяРегистра>`,
  `Измерение <ИмяИзмерения>`, `Реквизит <ИмяРеквизита>`.
- Если синоним, заголовок формы или бизнес-название отличается от имени
  метаданных, пиши его в скобках после имени:
  `Реквизит <ИмяРеквизита> (синоним: <Синоним>)`.
- Не используй в пользовательском тексте неподтвержденные сокращения и алиасы
  вроде `<АлиасДокумента>`, `<АлиасТаблицы>`, `<БизнесНазваниеПоля>`, если
  рядом нет расшифровки через объект метаданных.
- Алиасы запросов и переменные допустимы внутри фрагментов кода, но в пояснении
  должны быть сопоставлены с объектом метаданных.
- Если по алиасу нельзя надежно определить объект метаданных, не угадывай молча:
  пиши `предположительно` или выноси это в open/blocking question.
- Типы объектов метаданных называй на русском: `Документ`, `Справочник`,
  `Регистр накопления`, `Регистр сведений`, `Общий модуль`, `Обработка`,
  `Отчет`, `Модуль объекта`, `Модуль менеджера`, `Модуль формы`,
  `Модуль набора записей`.

## БСП и расширяемость

- Для содержательной работы со стандартными подсистемами БСП используй
  `.claude/skills/1c-bsp/SKILL.md`: он содержит workflow по переопределяемым
  точкам, project-wrapper-ам, вариантам отчетов, формам БСП и вспомогательным
  данным ИБ.
- Если в БСП или стандартных механизмах платформы уже есть подходящий метод или
  паттерн, предпочтителен он, а не новый самописный механизм.
- Изменения библиотечных или типовых подсистем должны быть осознанными и
  минимальными.

## Чтение реквизитов ссылочных объектов

- При обращении к объекту ссылочного типа через точку платформа читает объект
  целиком. Не используй серии обращений вида `Источник.Ссылка.Реквизит1`,
  `Источник.Ссылка.Реквизит2` для получения реквизитов из базы.
- Если нужен один реквизит ссылочного объекта, используй метод БСП
  `ОбщегоНазначения.ЗначениеРеквизитаОбъекта(Ссылка, "ИмяРеквизита")`.
- Если нужно несколько реквизитов одного и того же объекта, используй
  `ОбщегоНазначения.ЗначенияРеквизитовОбъекта(Ссылка, "Реквизит1, Реквизит2")`
  или один явный запрос.
- Два и более последовательных вызова `ЗначениеРеквизитаОбъекта` для одной
  ссылки в одном методе считаются дефектом, если нет явной причины читать
  реквизиты отдельно. Объединяй их в один `ЗначенияРеквизитовОбъекта` или
  один запрос.
- При добавлении нового чтения реквизита рядом с уже существующим чтением той
  же ссылки сначала проверь, не нужно ли заменить существующий одиночный вызов
  на пакетное чтение. Не оставляй рядом одиночные вызовы только потому, что
  один из них уже был в коде.
- Эти правила применяются ко всему коду 1С, включая production-код,
  обработчики событий, фоновые сценарии и тесты.

## Обращения к базе данных в циклах

- Не выполняй в цикле однотипные обращения к базе данных: запросы,
  `НайтиПоРеквизиту`, `НайтиПоКоду`, `НайтиПоНаименованию`,
  `ЗначениеРеквизитаОбъекта`, чтение реквизитов через точку от ссылки.
  Собери ключи заранее и получи все данные одним запросом с условием
  `В (&Массив)` в соответствие «ключ -> значение» (стандарт 1С #std436,
  диагностика `BSLLS:CreateQueryInCycle`).
- Правило распространяется на межметодный случай: вызов в цикле метода,
  который внутри выполняет запрос, — тот же дефект, хотя статический
  анализатор его не видит. Перед добавлением вызова метода в цикл проверь,
  не обращается ли он к базе; если обращается — вынеси получение данных до
  цикла и передай результат параметром или соответствием.
- Редко изменяющиеся данные (коды, настройки, константы, справочные таблицы)
  получай один раз до цикла, а не на каждой итерации.
- Исключение допустимо только с явно зафиксированной причиной в plan,
  tasklist, review или решении пользователя: например, порционная обработка,
  где данные обязаны быть актуальными на каждой итерации.

## Границы ответственности процедур и параметры

- Не добавляй параметр в процедуру или функцию, если она использует его только
  для транзитной передачи в другой вызов и не владеет поведением, которому этот
  параметр нужен.
- Перед изменением сигнатуры проверь, кому принадлежит действие: текущей
  процедуре, вызывающему оркестратору или отдельному helper. Размещай вызов на
  уровне, где уже есть необходимые данные и где находится смысловая
  ответственность за действие.
- Если процедура по назначению пишет один объект, регистр или контракт, не
  протаскивай в нее параметры, нужные только для записи другого объекта,
  регистра или контракта. Такой параметр обычно означает, что действие
  размещено не на своем уровне.
- Если нижняя процедура выполнила основное действие, а связанное действие
  относится к другому владельцу данных, предпочитай один из вариантов:
  поднять связанный вызов на уровень оркестратора, вернуть из нижней процедуры
  результат для оркестратора, выделить отдельный helper с явной
  ответственностью или зафиксировать осознанный trade-off в plan.
- Транзитный параметр допустим только при явном обосновании: например,
  стабильный публичный API, требование совместимости, единая транзакционная
  граница или локальный паттерн, подтвержденный в PRD, research, plan или
  решении пользователя.

## События записи и связанные объекты

- Если нужно записать связанный объект со ссылкой на новый объект, не выполняй
  такую запись в `ПередЗаписью` нового объекта, когда связанный объект должен
  сохранить уже валидную ссылку из базы.
- Для такой синхронизации используй `ПриЗаписи`: к этому моменту новый объект
  уже записан, а его ссылка пригодна для сохранения в связанных объектах.
- Если `ПриЗаписи` нужен контекст из `ПередЗаписью` (`РежимЗаписи`, `ЭтоНовый`
  или служебные данные формы), пробрасывай его через `ДополнительныеСвойства`.
  Пример:
  ```bsl
  ДополнительныеСвойства.Вставить("ЭтоНовый", ЭтоНовый());
  ДополнительныеСвойства.Вставить("РежимЗаписи", РежимЗаписи);
  ```
  В `ПриЗаписи` читай эти значения из `ДополнительныеСвойства`, а не вычисляй
  заново, если нужен именно контекст события `ПередЗаписью`.
- При массовой записи связанных ссылочных объектов внутри транзакции проверь,
  нужна ли явная `БлокировкаДанных`, чтобы избежать конфликтов параллельной
  записи одних и тех же объектов.

## Проверки уникальности и конкурентная запись

- Проверка «запросил — не нашёл — записал» (read-then-write) без блокировки не
  гарантирует уникальность: два параллельных сеанса проходят проверку
  одновременно и создают дубль. Обычный (неуникальный) индекс реквизита дубль
  не отсекает.
- Для гарантии уникальности по значению реквизита выполняй проверку в
  обработчике записи (`ПриЗаписи`) под управляемой блокировкой:
  `БлокировкаДанных` -> `Добавить("<Тип>.<Имя>")` ->
  `УстановитьЗначение("<Реквизит>", Значение)` ->
  `Режим = РежимБлокировкиДанных.Исключительный` -> `Заблокировать()`,
  затем поиск дубля с исключением самого себя (`Ссылка <> &Ссылка`).
- Блокировка объектной таблицы по обычному реквизиту требует двух парных
  шагов: `БлокировкаДанных` в BSL И объявление реквизита в свойстве метаданных
  `dataLockFields` объекта. Ошибка платформы «У пространства блокировок не
  существует поля с именем X» означает незаполненное `dataLockFields`, а не
  запрет платформы.
- Guard на пустое значение обязателен: без него все объекты с незаполненным
  реквизитом сериализуются по пустой ссылке и получают взаимные блокировки.
- Ранняя проверка на этапе заполнения допустима как быстрый отсев с понятным
  сообщением пользователю, но гарантией уникальности не является и блокировку
  не заменяет.

## Перенос логики между интерактивным и фоновым путями

- Метод, который вызывался из формы, часто опирается на проверки и гейты,
  живущие в вызывающем коде формы: контроль ошибок заполнения, вывод
  несопоставленных значений, подтверждения, отказ от записи.
- При переносе вызова такого метода в фоновый сценарий (обмен, регламентное
  задание, подписка на событие) проверь не только сам метод, но и то, что
  делал его прежний вызывающий. Потерянные проверки перенеси внутрь метода
  или в новый вызывающий код и покрой тестом.
- Если документирующий комментарий метода обещает контракт («при любой ошибке
  прерывает исключением»), фактическое поведение должно соответствовать
  контракту на всех путях вызова, а не только на интерактивном.

## Привилегированный режим и тестируемость

- Экспортность метода сама по себе не запрещает включать внутри него
  привилегированный режим. Опасен экспортный метод, который выполняет
  привилегированное действие безусловно для любого вызывающего.
- Если экспортный серверный метод включает привилегированный режим, сначала
  проверь функциональное право вызывающего и заверши отказом до включения
  режима. Привилегированный участок ограничивай действиями, которым он
  действительно нужен.
- Не оставляй прикладной серверный сценарий в модуле формы или команды только
  из-за наличия привилегированного участка. Сценарий можно вынести в подходящий
  серверный модуль с проверкой права перед включением режима, а форму или
  команду оставить тонким оркестратором.
- Для такого сценария отдельно проверяй разрешенный путь и отказ вызывающему
  без требуемого права; тест должен исполнять вынесенный production-entrypoint.

## Обработчики обновления ИБ

- Обработчик обновления обычно размещается в модуле менеджера обновляемого
  объекта.
- В каждой системе должен быть проектный общий модуль, который регистрирует
  обработчики обновления. Обычно он называется
  `ОбновлениеИнформационнойБазы<ИмяСистемы>`.
- Имя метода обработчика обновления должно заканчиваться на
  `ПриПереходеНаВерсию_<Номер_Версии>`, например
  `ЗаполнитьДатуНачалаДействияПриПереходеНаВерсию_1_0_6_5`.
- Если не удается надежно определить модуль менеджера обновляемого объекта,
  размещай обработчик в общем модуле
  `ОбновлениеИнформационнойБазы<ИмяСистемы>`.
- Добавляй только сам обработчик обновления и его регистрацию. Не меняй
  `Описание.Версия = "<НомерВерсии>"`, если пользователь явно не попросил
  изменить версию.
- Для обработчика обновления добавь модульный тест или явно зафиксируй, почему
  автоматический тест невозможен и какая ручная проверка его заменяет.

## Интеграции и обмены данными

- Изменение обмена, HTTP-сервиса, web-сервиса, загрузки/выгрузки, XDTO/JSON/XML
  пакета или другого интеграционного механизма считается изменением контракта.
- Перед реализацией должны быть явно зафиксированы направление обмена, формат
  данных, источник и назначение полей, точка запуска, поведение при ошибках и
  проверки.
- Reference pattern похожего обмена является источником инженерного подхода, но
  не источником требований. Поля, URL, HTTP-метод, фильтры, batching, права,
  версии API и тестовые сценарии переносятся только при наличии источника в PRD,
  research, project/path rules или явном решении пользователя.
- Если контрактные детали не определены, это `Open question` или `BLOCKER`, а
  не повод заполнить пробел по аналогии.
- При заполнении XDTO, JSON/XML-структур или других контрактных объектов из
  результата запроса сверяй тип выражения в SELECT с типом поля контракта. Если
  поле контракта ссылочного типа, запрос должен возвращать ссылку; если поле
  ожидает UUID или строку, возвращай UUID или строку явно. Не подменяй тип
  результата удобным представлением без проверки потребителя.

## Тестирование

- Если задача изменяет поведение системы, нужно либо добавить или обновить тест,
  либо явно зафиксировать причину отсутствия теста и план ручной проверки.
- Для тестовых артефактов могут действовать более узкие project-specific правила.

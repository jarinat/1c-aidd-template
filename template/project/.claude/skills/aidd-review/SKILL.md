# AIDD Review

Используй subagent `reviewer`.

Source of truth:

- lifecycle `review` и связанные статусы:
  - `.claude/rules/core/aidd-workflow.md`
  - `.claude/rules/core/aidd-artifacts.md`
- выбор инструментов и tooling gaps:
  - `.claude/rules/core/tool-usage.md`
- общая политика code review:
  - `.claude/rules/core/code-review.md`

## Границы выполнения

- Review выполняется через subagent `reviewer`.
- Основная сессия читает AIDD-артефакты, запускает `reviewer`, сохраняет
  результат review и запрашивает решение пользователя по открытым замечаниям.
- AIDD-артефакты (`prd`, `plan`, `tasklist`, `feedback`, `review`) читай
  напрямую.
- Все 1С/EDT проекты этого шаблона считаются большими кодовыми базами.
  Discovery по 1С-коду основная сессия и `reviewer` начинают через
  `.claude/skills/1c-rsv-tools/SKILL.md`, если MCP `1c-rsv` доступен.
- Основная сессия не собирает большие фрагменты 1С-кода вручную перед запуском
  `reviewer`. Передавай agent краткую discovery-сводку: projectName,
  использованные helpers, найденные объекты, методы, формы, узкие
  файлы-кандидаты и ограничения проверки.
- `Read`, `Glob` и `Grep` используй для точного подтверждения найденных
  кандидатов или как fallback, если MCP недоступен, `projectName` не определен
  или helper не помогает.
- Не начинай review/research с широкого `git diff main...HEAD`, `Glob`/`Grep`
  по `src`, `src/cf`, `src/cfe` или чтения целых модулей, если область можно
  сузить через активный тикет, AIDD-артефакты и `1c-rsv`.
- Если `1c-rsv` недоступен или не может дать нужный контекст, явно
  зафиксируй это ограничение в review и только затем переходи к fallback.
- MCP discovery не заменяет чтение подтверждающих исходников: каждое blocking
  или important замечание должно ссылаться на конкретный файл, метод, XML-узел,
  AIDD-артефакт или diff.
- Если встроенных инструментов недостаточно из-за проблем Windows, кодировки или
  кириллических путей, основная сессия может собрать недостающий read-only
  контекст только через универсальный helper:
  `.claude/scripts/aidd-inspect.cmd ...`.
- Перед запуском `reviewer` основная сессия должна подготовить карту diff через
  `.claude/scripts/aidd-inspect.cmd review-diff summary`. Если diff затрагивает
  `.bsl`, дополнительно используй `review-diff bsl`; если затрагивает
  `.mdo`, `.dcs`, `.form`, `.rights` или другой EDT XML, дополнительно
  используй `review-diff metadata`.
- Если MCP `bsl-ls` доступен и diff затрагивает `.bsl`, механический слой
  проверяется по `.claude/skills/bsl-ls-tools/SKILL.md`: `analyze_file` по
  каждому изменённому `.bsl`, фильтрация диагностик к изменённым строкам,
  результат передаётся `reviewer` как вход. Если MCP недоступен, это
  фиксируется как ограничение review, а механический слой не считается
  проверенным.
- Нельзя передавать `reviewer` только первые N строк diff или делать вывод по
  усеченному diff. Если полный diff слишком большой, передай summary, список
  файлов, чувствительные секции из helper-а и точные файлы/фрагменты для
  проверки. Ограничение полноты фиксируй как review limitation.
- Не используй inline `Bash`, `python`, `python3 -c`, compound shell scripts,
  `for ...; do`, `find | grep | head` и другие произвольные shell-обходы.
- Если `reviewer` не может завершить проверку доступными инструментами,
  а helper не помогает, остановись и сообщи пользователю, какой контекст не
  удалось получить.

## Алгоритм

1. Определи ticket id: используй переданный аргумент или `aidd/docs/.active_ticket`.
2. Прочитай PRD, plan, tasklist, `feedback` и существующий `review`, если он
   уже есть.
3. Если MCP `1c-rsv` доступен, выполни краткий discovery-проход по
   объектам, методам, формам и тестам тикета; если недоступен, зафиксируй
   fallback-ограничение.
4. Подготовь карту diff:
   - `review-diff summary`;
   - `review-diff bsl`, если изменены `.bsl`;
   - `review-diff metadata`, если изменены `.mdo`, `.dcs`, `.form`,
     `.rights` или EDT XML;
   - если MCP `bsl-ls` доступен и изменены `.bsl` — механические диагностики
     по `.claude/skills/bsl-ls-tools/SKILL.md` (только по изменённым строкам).
5. Запусти `reviewer`, передав AIDD-контекст, discovery-сводку, карту diff
   и отфильтрованные диагностики `bsl-ls` вместо больших фрагментов кода.
6. Проверь:
   - соответствие PRD и plan;
   - именование новых полей, колонок и реквизитов относительно исходной задачи,
     таблицы соответствия PRD и `.claude/rules/project/naming.md`;
   - отсутствие новых неутвержденных сокращений в локальных именах кода, если
     они обозначают объекты метаданных или их элементы: процедуры, функции,
     helper'ы, переменные, параметры, поля структур, fixture-поля, тестовые
     методы и сценарии;
   - последовательные чтения реквизитов одной ссылки: несколько
     `ОбщегоНазначения.ЗначениеРеквизитаОбъекта` рядом должны быть объединены в
     `ЗначенияРеквизитовОбъекта` или обоснованы;
   - новые и измененные сигнатуры: нет ли параметров, которые используются
     только для транзитной передачи дальше; соответствует ли каждый параметр
     ответственности процедуры или функции;
   - размещение связанных действий: не ушла ли запись другого регистра,
     объекта или контракта в процедуру, которая по названию и назначению
     отвечает за другой владелец данных; если ушла, есть ли обоснование в
     PRD, plan, tasklist, project/path rule или решении пользователя;
   - переименования объектов и элементов метаданных: изменены mdo-имена и
     связанные ссылки, а не только синонимы/заголовки, если пользователь явно не
     указал обратное;
   - удаления элементов метаданных: есть диагностика удаления, решения по всем
     `USED` и `UNCLEAR` точкам, повторный поиск обращений после удаления и
     EDT validation;
   - `Reference pattern`: контрактные детали, поля, фильтры, настройки формы,
     права, транспортные параметры, форматы данных, URL, HTTP-методы, версии API,
     batching-логика и другие элементы scope не были перенесены из аналога без
     источника в PRD, research, plan, tasklist, project/path rule или явном
     решении пользователя;
   - тесты: тестовые сценарии и ожидаемые данные не были просто "сняты с
     аналога" без связи с требованиями, plan или проверяемым production-путем;
   - закрытие пользовательских замечаний из `feedback`;
   - соблюдение project rules, core rules и path rules;
   - безопасность;
   - достаточность тестов и проверок.
7. Сформулируй замечания по категориям `blocking`, `important`, `minor`.
8. Сохрани результат в `aidd/docs/review/<ticket>.md`:
   - не смешивай `review` с `feedback`;
   - для новых замечаний создавай записи `RV-XXX`;
   - фиксируй статус, категорию, место проблемы, описание и решение.
   - если `reviewer` сообщил `Tooling gap`, зафиксируй его отдельным разделом
     или подпунктом ограничения проверки.
9. Если видишь пропуски в декомпозиции, предложи добавить задачи в tasklist, но
   не правь его автоматически.
10. После сохранения review запроси решение пользователя по незакрытым замечаниям.
11. Автоматические исправления не запускай; для этого есть `aidd-fix-review`.

## Режим Pre-MR: review всей ветки

Назначение: один финальный прогон перед созданием или обновлением MR, когда
ветка содержит несколько подтикетов. Обычный review проверяет change-set
активного тикета и якорится на его PRD/plan; режим Pre-MR закрывает классы,
невидимые из одного подтикета: кросс-подтикетные дефекты, неполно применённые
решения по классу дефекта и дефекты, унаследованные из самих артефактов.

Запуск: по явной просьбе пользователя («pre-MR review», «review всей ветки»)
или по предложению основной сессии перед отправкой MR — с подтверждением
пользователя, так как это дополнительный полный прогон.

Отличия от обычного алгоритма:

1. Diff берётся по всей ветке: `<target>...HEAD` (обычно `develop...HEAD`).
   Карта diff готовится теми же subcommand `review-diff` с явным refspec.
2. Механический слой `bsl-ls` прогоняется по всем изменённым `.bsl` ветки,
   если MCP доступен.
3. `reviewer` запускается с anti-anchor инструкцией вместо якоря на PRD:
   - PRD/plan подтикетов — вход и claim, а не доказательство корректности;
     оценивай поведение системы глазами внешнего ревьюера;
   - тихие дефолты: нераспознанное значение молча превращается в 0, пустую
     дату, пустую строку или пропуск строки без сигнала об ошибке;
   - потерянные проверки вызывающих при переносе логики между интерактивным
     и фоновым путями;
   - если по классу дефекта в ветке принято решение (исправлено одно место),
     проверь, что класс закрыт во всех подтикетах и соседних местах того же
     модуля;
   - консистентность именования, локализации, UX ошибок и контрактов между
     подтикетами одной ветки;
   - обоснованность имён, прав и контрактных деталей без опоры на PRD: у
     каждого должен быть источник — исходная задача, стандарт, project rule
     или решение пользователя; если источника нет, это open question, а не
     PASS.
4. Замечания фиксируются в review активного тикета обычными записями `RV-XXX`
   с указанием источника `pre-MR review <refspec>`. Дедупликация — по всем
   `aidd/docs/review/<tracker-ticket>-*.md`, как для импорта Sonar и
   комментариев MR.
5. Остальные правила обычного review не меняются: категории замечаний,
   решения пользователя, `aidd-fix-review`, запрет автоматических исправлений.

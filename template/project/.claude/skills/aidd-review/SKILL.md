# AIDD Review

Используй subagent `reviewer`.

Source of truth:

- lifecycle `review` и связанные статусы:
  - `.claude/rules/core/aidd-workflow.md`
  - `.claude/rules/core/aidd-artifacts.md`
- общая политика code review:
  - `.claude/rules/core/code-review.md`

## Границы выполнения

- Review выполняется через subagent `reviewer`.
- Основная сессия читает AIDD-артефакты, запускает `reviewer`, сохраняет
  результат review и запрашивает решение пользователя по открытым замечаниям.
- Основной путь чтения и поиска файлов в рамках review: `Read`, `Glob` и `Grep`.
- Если доступен MCP `rlm-tools-bsl`, `reviewer` может использовать
  `.claude/skills/rlm-tools-bsl/SKILL.md` как read-only discovery слой для
  проверки reference pattern, callers, метаданных, форм, движений, подписок,
  интеграций и рисков регрессии за пределами diff.
- MCP discovery не заменяет чтение подтверждающих исходников: каждое blocking
  или important замечание должно ссылаться на конкретный файл, метод, XML-узел,
  AIDD-артефакт или diff.
- Если встроенных инструментов недостаточно из-за проблем Windows, кодировки или
  кириллических путей, основная сессия может собрать недостающий read-only
  контекст только через универсальный helper:
  `powershell -NoProfile -ExecutionPolicy Bypass -File .claude/scripts/aidd-inspect.ps1 ...`.
- Не используй inline `Bash`, `python`, `python3 -c`, compound shell scripts,
  `for ...; do`, `find | grep | head` и другие произвольные shell-обходы.
- Если `reviewer` не может завершить проверку доступными инструментами,
  а helper не помогает, остановись и сообщи пользователю, какой контекст не
  удалось получить.

## Алгоритм

1. Определи ticket id: используй переданный аргумент или `aidd/docs/.active_ticket`.
2. Прочитай PRD, plan, tasklist, `feedback` и существующий `review`, если он
   уже есть.
3. Запусти `reviewer`.
4. Проверь:
   - соответствие PRD и plan;
   - именование новых полей, колонок и реквизитов относительно исходной задачи,
     таблицы соответствия PRD и `.claude/rules/project/naming.md`;
   - отсутствие новых неутвержденных сокращений в локальных именах кода, если
     они обозначают объекты метаданных или их элементы: процедуры, функции,
     helper'ы, переменные, параметры, поля структур, fixture-поля, тестовые
     методы и сценарии;
   - переименования объектов и элементов метаданных: изменены mdo-имена и
     связанные ссылки, а не только синонимы/заголовки, если пользователь явно не
     указал обратное;
   - удаления элементов метаданных: есть диагностика удаления, решения по всем
     `USED` и `UNCLEAR` точкам, повторный поиск обращений после удаления и
     EDT validation;
   - `Reference pattern`: контрактные детали, поля, фильтры, настройки формы,
     права, транспортные параметры, форматы данных, URL, HTTP-методы, версии API,
     batching-логика и другие элементы scope не были перенесены из аналога без
     источника в PRD, research, plan, tasklist, project/path rule или явном
     решении пользователя;
   - тесты: тестовые сценарии и ожидаемые данные не были просто "сняты с
     аналога" без связи с требованиями, plan или проверяемым production-путем;
   - закрытие пользовательских замечаний из `feedback`;
   - соблюдение project rules, core rules и path rules;
   - безопасность;
   - достаточность тестов и проверок.
5. Сформулируй замечания по категориям `blocking`, `important`, `minor`.
6. Сохрани результат в `aidd/docs/review/<ticket>.md`:
   - не смешивай `review` с `feedback`;
   - для новых замечаний создавай записи `RV-XXX`;
   - фиксируй статус, категорию, место проблемы, описание и решение.
7. Если видишь пропуски в декомпозиции, предложи добавить задачи в tasklist, но
   не правь его автоматически.
8. После сохранения review запроси решение пользователя по незакрытым замечаниям.
9. Автоматические исправления не запускай; для этого есть `aidd-fix-review`.

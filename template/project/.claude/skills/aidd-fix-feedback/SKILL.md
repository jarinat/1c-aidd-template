# AIDD Fix Feedback

Используй subagent `feedback-fixer`.

Source of truth для lifecycle `feedback` и статусов:

- `.claude/rules/core/aidd-workflow.md`
- `.claude/rules/core/aidd-artifacts.md`
- `.claude/rules/core/tool-usage.md`

## Ключевые правила

- Один запуск = одно замечание `FB-XXX`.
- Если пользователь согласовал несколько замечаний сразу, основная сессия
  запускает `feedback-fixer` последовательно по каждому `FB-XXX`.
- Этот workflow не обновляет `tasklist` и не делает commit.
- Не запускай `implementer` внутри этого сценария.
- Для `feedback` используются только статусы `OPEN`, `RESOLVED` и `DECLINED`.
- `RESOLVED` ставится только основной сессией после явного ответа пользователя
  “всё ок”.
- Фразы пользователя вроде "предлагаю попробовать", "проверим на одном
  элементе", "сначала выяснить причину" или "чтобы не гадать" не считаются
  согласием на исправление. Пробная правка одного элемента тоже является
  исправлением и требует записи рекомендации в `feedback` и отдельного согласия
  пользователя после этой рекомендации.
- Если пользователь говорит "фиксируем", "добавляем", "берем в работу" или
  "давай сделаем" в контексте замечаний, сначала зафиксируй замечание в
  `feedback`; эти слова сами по себе не разрешают пропустить запись `FB-XXX`.
- Если пользователь согласовал несколько замечаний без существующих `FB-XXX`,
  создай отдельные записи `FB-001`, `FB-002`, ... для каждого самостоятельного
  замечания, зафиксируй рекомендацию и решение пользователя, затем обрабатывай
  записи последовательно.

## Алгоритм

1. Определи ticket id: используй переданный аргумент или `aidd/docs/.active_ticket`.
2. Определи целевую запись `FB-XXX`:
   - используй переданный аргумент, если он есть;
   - иначе используй явно упомянутый пользователем `FB-XXX`;
   - если однозначно определить нельзя, задай один короткий уточняющий вопрос.
3. Прочитай `aidd/docs/feedback/<ticket>.md`, если файл существует. Если
   целевая запись уже есть, найди её.
4. Если замечание ещё не зафиксировано, сначала найди причину и вариант
   решения, затем создай запись `FB-XXX` со статусом `OPEN`, анализом и
   рекомендацией.
   - если само замечание пользователя связано с YAxUnit-тестами, тестовым
     расширением, Мокито, assertions, test doubles или YAxUnit API, основная
     сессия применяет `.claude/skills/yaxunit-tests/SKILL.md` до анализа причины
     и формулирования рекомендации в feedback;
   - нельзя откладывать `yaxunit-tests` только до этапа `feedback-fixer`, если в
     feedback записывается технический вывод по тесту.
5. Перед исправлением убедись, что пользователь согласовал рекомендацию. Если
   согласия нет, покажи рекомендацию и остановись до решения пользователя.
6. Прочитай связанный код и контекст тикета.
7. Запусти `feedback-fixer` со scope ровно текущего `FB-XXX`.
   - если замечание затрагивает YAxUnit-тесты, тестовое расширение, Мокито,
     `ЮТест.Данные()`, assertions, test doubles или YAxUnit API, явно укажи
     `feedback-fixer`, что он обязан применить
     `.claude/skills/yaxunit-tests/SKILL.md`;
   - чтение `.claude/skills/yaxunit-tests/references/api-reference.md` не
     заменяет применение `.claude/skills/yaxunit-tests/SKILL.md`;
   - для API YAxUnit, Мокито, HTTP-моков, `HTTPОтвет`, `HTTPСервисЗапрос` или
     `&Вместо` отдельно укажи прочитать
     `.claude/skills/yaxunit-tests/references/api-reference.md`.
8. Проверь результат и обнови запись в `aidd/docs/feedback/<ticket>.md`:
   - зафиксируй фактическое исправление;
   - перечисли изменённые файлы;
   - укажи, что проверка ожидает пользователя;
   - если `feedback-fixer` сообщил `Tooling gap`, зафиксируй его в записи
     `FB-XXX` отдельным полем или подпунктом, не меняя рекомендацию задним
     числом;
   - оставь статус `OPEN`, пока пользователь не подтвердил "всё ок".
9. Сообщи пользователю:
   - что изменено;
   - какие файлы затронуты;
   - что теперь нужно проверить;
   - что замечание ещё не переведено в финальный статус.
10. Попроси пользователя проверить результат.
11. Если пользователь сообщает, что проблема осталась, продолжай работать с тем
   же `FB-XXX`, не создавая новую запись.
12. Если пользователь подтверждает, что всё ок, основная сессия обновляет
   `feedback`: ставит `RESOLVED`, фиксирует проверку, предлагает текст commit,
   но не делает commit автоматически.

# bsl-ls-tools

Этот skill описывает правила использования MCP-сервера `bsl-ls` (BSL Language
Server). Сервер читает исходники рабочей копии и отдаёт диагностики BSLLS и
языковую навигацию по BSL.

`bsl-ls` не заменяет выбранный EDT MCP. Метаданные, формы, СКД, роли,
EDT-валидация и все правки остаются в зоне соответствующего ему skill. `bsl-ls`
закрывает два независимых слоя:

- механические диагностики BSLLS (регистр ключевых слов, смешение латиницы и
  кириллицы в идентификаторах, дубли строковых литералов, буква `Ё`, длина
  строк, когнитивная сложность, запрос в цикле и другие правила
  bsl-language-server) — до SonarQube и до MR;
- языковую навигацию уровня BSL: `find_references`, `call_hierarchy`,
  `definition`, `document_symbols`.

`bsl-ls` привязан к рабочей копии, на которую настроен сервер. В изолированном
review worktree (`review-gitlab-mr`) его применимость не подтверждена — там не
использовать, пока применимость не проверена отдельно.

## Когда использовать

- Review изменённых `.bsl`: прогон диагностик по каждому файлу из карты diff.
- Caller-анализ: кто вызывает изменённый метод, не потерялись ли проверки
  вызывающих (`find_references`, `call_hierarchy`).
- Поиск платформенного глобального метода или свойства по неточному имени
  (`global_member_search`, `global_member_info`).
- Уточнение типа выражения или сигнатуры в спорной точке (`hover`,
  `type_at_position`, `type_info`).

## Когда не использовать

- Для правок кода — только read-only анализ.
- Для метаданных, форм, СКД и ролей — выбранный EDT MCP.
- Для поиска методов БСП/конфигурации — semantic tools выбранного EDT MCP
  (глобальный контекст `bsl-ls` покрывает платформу, а не общие модули).
- Как единственное основание blocking/important замечания: диагностика —
  указатель, подтверждай чтением исходника.

## Workflow: механический слой review

1. Возьми список изменённых `.bsl` из карты diff (`review-diff summary`).
2. Для каждого файла вызови `analyze_file`.
3. Отфильтруй результат: в отчёт review идут только диагностики, попадающие в
   изменённые строки diff, либо порождённые изменёнными методами. Диагностики
   в незатронутом коде — преэкзистентный фон; их не выноси как замечания
   тикета, при желании зафиксируй одной строкой как наблюдение.
4. Непонятный код диагностики расшифруй через `v8std_explain_diagnostics`
   (`.claude/skills/v8std-tools/SKILL.md`), а не по памяти.
5. Подтверждённые находки оформи как замечания review с указанием кода
   правила (например, `BSLLS:CanonicalSpellingKeywords`); шумные или
   неприменимые правила отклоняй с причиной.
6. Механические классы, покрытые диагностиками, не перепроверяй вручную.
   Если MCP недоступен, зафиксируй это как ограничение review — механический
   слой в этом случае не считается проверенным.

## Workflow: caller-анализ

1. Для изменённого или перенесённого метода получи вызывающих:
   `find_references` или `call_hierarchy`.
2. Проверь каждого вызывающего на проверки и гейты, которые он выполняет
   вокруг вызова (см. `.claude/rules/core/onec-general.md`, раздел про перенос
   логики между путями).
3. Результаты сверь с semantic references выбранного EDT MCP, если они
   доступны и список вызывающих критичен для вывода.

## Формат фиксации

Когда `bsl-ls` повлиял на вывод, фиксируй коротко:

```text
MCP bsl-ls:
- scope: <файлы из карты diff, по которым прогнан analyze_file>
- findings: <N диагностик в изменённых строках -> M замечаний review>
- dropped: <отклонённые правила и причина>
- limitations: <MCP недоступен / файл вне workspace / ...>
```

# AIDD Tasks

Используй subagent `task-planner`.

Source of truth для lifecycle артефактов и статусов:

- `.claude/rules/core/aidd-artifacts.md`
- `.claude/rules/core/aidd-workflow.md`
- `.claude/rules/core/code-style.md`

## Алгоритм

1. Определи ticket id: используй переданный аргумент или `aidd/docs/.active_ticket`.
2. Прочитай PRD и plan.
3. Если PRD/plan вводят новые поля, колонки или реквизиты, убедись, что
   tasklist наследует mdo-имена без переименования и без новых сокращений. При
   расхождении с таблицей соответствия PRD не создавай tasklist по затронутой
   части; верни блокер на PRD/plan.
4. Если PRD/plan включают переименование объектов или элементов метаданных,
   убедись, что tasklist наследует именно переименование mdo-имён по
   `.claude/rules/project/naming.md`, а не подменяет его изменением
   синонимов/заголовков.
5. Если PRD/plan включают удаление элементов метаданных:
   - убедись, что plan ссылается на research-диагностику удаления;
   - убедись, что по всем `USED` и `UNCLEAR` точкам есть явные пользовательские
     решения после обсуждения с аналитиком/бизнесом;
   - если решений нет, не создавай tasklist по затронутой части и верни blocker
     на plan/research/decision gate.
6. Убедись, что plan готов к декомпозиции по правилам AIDD.
7. Перед декомпозицией проверь, что plan отделяет `Reference pattern` от
   подтвержденных решений:
   - tasklist может наследовать только те контрактные, проектные, UI, data,
     rights, transport, testing и другие scope-решения, которые подтверждены
     PRD, research, входным артефактом, project/path rule или явным решением
     пользователя;
   - если деталь есть только в аналоге или reference pattern, не превращай ее в
     задачу, DoD или acceptance-критерий;
   - если без такой детали нельзя безопасно декомпозировать блок, верни blocker
     на plan/research/пользователя, а не заполняй пробел по аналогии.
8. Для каждого change-блока перенеси из plan `Implementation pattern` в
   `Reference pattern`:
   - укажи конкретный файл/объект/метод или другой локальный аналог, на который
     должен опираться implementer;
   - явно отдели, что implementer должен наследовать из reference pattern, а
     какие отличия или контрактные детали подтверждены источниками из plan;
   - если для блока нужен осознанный отход от локального паттерна, перенеси
     причину отклонения из plan;
   - если в plan нет implementation pattern для затронутой зоны, верни блокер
     на уточнение plan, а не создавай tasklist с неявным паттерном.
9. Не добавляй в tasklist задачи или DoD на добавление комментариев к новым
   методам. Исключение — полноценная EDT-документация экспортного метода, если
   это явно требуется программным интерфейсом или пользователем.
10. Для YAxUnit не создавай задачи на комментарии `Подготовка`, `Действие`,
   `Проверка` и EDT-документацию экспортных тестовых процедур.
11. Создай `aidd/docs/tasklist/<ticket>.md`.
12. Оформляй tasklist через явные блоки вида `## Блок N: ...`.
13. Внутри каждого блока фиксируй задачи-чекбоксы, `Reference pattern` и DoD.
14. В DoD каждого implementation-блока добавляй проверку, что реализация
    соответствует `Reference pattern` или отклонение явно описано в plan/tasklist.
15. Для удалений элементов метаданных добавляй отдельный verification-only блок:
    повторный поиск обращений к удаленному элементу, EDT validation, проверка
    форм/СКД/ролей/обменов в scope и релевантные тесты или ручные проверки.
16. Для проверок и EDT-валидации выделяй отдельные verification-only блоки.
17. Даже если в блоке одна задача, блок всё равно должен быть явным.

## Структура tasklist

- статус готовности по правилам AIDD
- явные change-блоки
- задачи внутри каждого блока
- `Reference pattern` внутри каждого implementation-блока
- перечень наследуемых из `Reference pattern` элементов и подтвержденных
  источниками отличий/контрактных деталей
- DoD для задач
- DoD-проверка соответствия `Reference pattern` или явно описанного отклонения
- verification-only блоки
- отдельная verification-проверка именования новых полей, колонок и
  реквизитов относительно таблицы соответствия PRD, если они есть
- отдельная verification-проверка, что переименования объектов и элементов
  метаданных изменяют mdo-имена и связанные ссылки, если такие переименования
  есть
- отдельный verification-only блок пост-проверки удаления элементов метаданных,
  если задача включает удаление

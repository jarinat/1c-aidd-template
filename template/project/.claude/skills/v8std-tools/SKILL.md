# v8std-tools

Этот skill описывает правила использования MCP-сервера `v8std`. Сервер —
read-only источник знаний по стандартам 1С (v8std.ru): тексты стандартов,
описания диагностик BSLLS, АПК и EDT/v8-code-style, связи между ними.

`v8std` не анализирует проект и не запускает проверки. Он отвечает на вопрос
«что говорит стандарт», а не «что не так в этом файле». Факты об исходниках,
метаданных и EDT-валидации проверяй через skill выбранного EDT MCP.

`v8std` не привязан к workspace или рабочей копии, поэтому разрешён и в
сценариях review в изолированном worktree (`review-mr`, `review-gitlab-mr`).

## Когда использовать

- Review нашёл спорный паттерн и нужно отличить нарушение стандарта от
  вкусового замечания.
- Нужно расшифровать код диагностики анализатора: что проверяет правило, какой
  стандарт за ним стоит.
- Перед реализацией или в plan/research нужно подтвердить, что выбранный
  паттерн (транзакции, блокировки, запросы, обработчики) соответствует
  стандартам 1С.
- Замечанию review нужен авторитетный источник: ссылка на стандарт усиливает
  замечание и снимает спор.

## Когда не использовать

- Для фактов о коде проекта, метаданных или формах — выбранный EDT MCP / `Read`.
- Как замену решения пользователя: стандарт — аргумент, а не решение по
  scope. Отступление от стандарта может быть осознанным и зафиксированным.

## Выбор инструмента

- `v8std_explain_snippet` — короткий фрагмент BSL/SDBL: какие стандарты и
  диагностики к нему относятся.
- `v8std_explain_diagnostics` — код диагностики (`BSLLS:CreateQueryInCycle`,
  `АПК:482`, `query-in-loop`): описание, важность, связанный стандарт.
- `v8std_get_page` — полный текст страницы по известному id/alias/URL
  (например, `std436`).
- `v8std_get_related` — переход от стандарта к связанным диагностикам и
  обратно.
- `v8std_search` — поиск по произвольной формулировке, когда id неизвестен.

## Правила использования в review

- Замечание, опирающееся на стандарт, фиксируй со ссылкой: id стандарта или
  диагностики и URL (например, `#std436`,
  `https://v8std.ru/std/436/`).
- Не выдавай пересказ стандарта по памяти за его текст: если стандарт цитируешь
  как основание blocking/important замечания, сначала получи страницу через
  `v8std_get_page` или `v8std_explain_diagnostics`.
- Стандарт не отменяет более узкие project rules: при конфликте действует
  приоритет источников из `.claude/CLAUDE.md`.
- Если MCP недоступен, не блокируй review: зафиксируй ограничение и опирайся
  на project/core rules.

## Формат фиксации

Когда `v8std` повлиял на вывод, фиксируй коротко:

```text
MCP v8std:
- source: <std id / diagnostic id + URL>
- statement: <одно предложение — что говорит стандарт>
- applied to: <файл/метод/замечание>
```

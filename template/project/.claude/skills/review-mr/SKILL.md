# Review Merge Request

Используй subagent `review-mr`.

Source of truth:

- общая политика code review:
  - `.claude/rules/core/code-review.md`
- специализированные проверки:
  - `1c-query`
  - `edt-form-editing`
  - `yaxunit-tests`

Важно: в `review-mr` не используй `rlm-tools-bsl` и связанные MCP-инструменты.
MR review может выполняться в отдельном worktree, а индекс RLM может относиться
к другой рабочей копии. Для discovery используй `git diff`, `Read`, `Glob`,
`Grep` и локальное чтение файлов в правильном worktree.

## Алгоритм

1. Проверь, что задана одна из пар входов:
   - `SOURCE_BRANCH` и `TARGET_BRANCH`;
   - `BASE_REF` и `HEAD_REF`.
2. Если задан `REVIEW_WORKTREE`, выполняй все `git diff`, `git show`, `rg` и
   чтение файлов только внутри этого worktree. Не используй текущую рабочую
   копию пользователя для surrounding context.
3. Получи актуальный diff:
   - для веток:
     - `git fetch origin $SOURCE_BRANCH $TARGET_BRANCH`
     - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH --stat`
     - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH --name-status --find-renames`
     - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH --find-renames`
   - для refs/SHA:
     - `git diff $BASE_REF...$HEAD_REF --stat`
     - `git diff $BASE_REF...$HEAD_REF --name-status --find-renames`
     - `git diff $BASE_REF...$HEAD_REF --find-renames`
4. Просмотри список затронутых файлов и оцени общий риск изменений.
5. Для рискованных изменений не ограничивайся только hunks из diff: прочитай
   окружающий метод, связанные процедуры, вызывающие места, модуль формы или
   тестовый модуль, если без этого нельзя уверенно оценить поведение.
6. Для каждого существенного изменения определи локальный паттерн реализации в
   том же модуле, объекте, форме или подсистеме, если такой паттерн есть.
7. Проведи review diff с фокусом на:
   - behavioural regressions и нарушения бизнес-логики;
   - явное дублирование и упущенное переиспользование;
   - читаемость, вложенность и перегруженные условия;
   - неоптимальные алгоритмы, запросы к базе в циклах и лишние обходы;
   - соответствие локальному паттерну текущего модуля, объекта, формы или
     подсистемы;
   - рассинхрон EDT-форм и связанного кода;
   - именование и структуру YAxUnit-тестов, если они затронуты.
8. Отдельно проверь добавленные строки кода на англоязычные операторы 1С вроде
   `If`, `Then`, `Else`, `Function`, `Procedure`, `Return`, `Try`, `And`, `Or`,
   `Break`, `Continue`, кроме комментариев, строковых литералов и частей
   идентификаторов. Для запросов 1С также проверяй англоязычные ключевые слова
   через skill `1c-query`.
9. Сгруппируй замечания по категориям:
   - `blocking` — неправильный результат, runtime-ошибка, потеря данных,
     критичная деградация производительности, сломанная форма, неработающий
     тест или грубое нарушение, после которого MR нельзя принимать;
   - `important` — доказуемый архитектурный, алгоритмический риск или риск
     поддерживаемости, который не обязан ломать поведение прямо сейчас, но
     должен быть исправлен до завершения работы;
   - `minor` — локальные улучшения читаемости и неопасные замечания без
     существенного риска для поведения.
10. Каждое замечание формулируй по фактам:
   - где найдено;
   - в чём проблема;
   - почему это важно;
   - как исправить или что проверить дополнительно.
11. Подготовь итоговый отчёт:
   - краткая статистика по diff;
   - список замечаний по категориям;
   - повторяющиеся проблемные паттерны, если они реально видны в MR;
   - явная фиксация, что замечаний нет, если review чистый.

## Специализированные проверки

### Локальные паттерны реализации

- Так как MR других разработчиков может не иметь AIDD `plan/tasklist`, не ищи
  `Reference pattern` в AIDD-артефактах по умолчанию.
- Для каждого существенного изменения найди ближайший локальный аналог:
  - в том же модуле;
  - в том же объекте метаданных;
  - в той же форме и связанном `Module.bsl`;
  - в соседнем общем модуле или подсистеме, если в текущем модуле аналога нет.
- Проверь, что новая реализация соответствует локальному паттерну по:
  - месту размещения логики;
  - способу декомпозиции методов;
  - работе с запросами, временными таблицами и менеджерами;
  - обработке ошибок и возврату результата;
  - стилю вызова БСП/общих модулей;
  - именованию методов, переменных, реквизитов, элементов формы и тестов.
- Проверяй, что новый код не вводит локальные сокращения для объектов
  метаданных и их элементов: `PO`, `Spec`, `Спец`, буквенные/числовые суффиксы
  вместо роли и похожие алиасы. В именах процедур, helper'ов, переменных,
  параметров, полей структур, fixture-полей и тестов используй полное имя
  объекта метаданных и уточняющее слово по роли, если нужно различить несколько
  однотипных значений.
- Если одно такое сокращение найдено, проверь весь diff на тот же паттерн.
  Точные имена метаданных, реквизитов, табличных частей и внешних контрактов не
  считай нарушением только из-за краткости.
- Не требуй слепого повторения старого кода, если локальный паттерн является
  антипаттерном или противоречит более узким правилам `1c-query`,
  `edt-form-editing`, `yaxunit-tests`.
- Если локальный паттерн не найден, явно зафиксируй ограничение проверки и
  оценивай изменение по core rules и специализированным skills.
- Замечание по отклонению от локального паттерна давай только при доказуемом
  риске: дублирование механизма, рассинхрон с модулем, ухудшение
  сопровождаемости, обход БСП/расширяемости или риск регрессии.

### EDT-формы

- Если в diff затронут `Form.form`, проверяй не только XML, но и связь формы с
  кодом.
- Ищи рассинхрон между `name` и обращениями через `Элементы.<Имя>`.
- Ищи рассинхрон между `commandName` и секцией `<formCommands>`.
- Сопоставляй обработчики из `Form.form` с процедурами в `Module.bsl`.
- Проверяй уникальность новых `id` и корректность контейнера для нового
  элемента.

### YAxUnit

- Если в diff есть YAxUnit-тесты, отдельно проверяй именование тестовых
  модулей и методов через skill `yaxunit-tests`.
- Если diff затрагивает Мокито, `ЮТест.Данные()`, assertions, test doubles,
  `HTTPОтвет`, `HTTPСервисЗапрос`, `&Вместо` или другой YAxUnit API, применяй
  skill `yaxunit-tests` и его `references/api-reference.md` до формулирования
  замечаний. Чтение reference-файла не заменяет применение
  `.claude/skills/yaxunit-tests/SKILL.md`.
- Проверяй, что имя тестового модуля соответствует соглашению из
  `yaxunit-tests`: `[Префикс типа объекта]_[Имя объекта]{_Суффикс типа модуля}`.
- Проверяй, что используются кириллические префиксы типов объектов: `ОМ_`,
  `Док_`, `Спр_`, `Обр_`, `РН_`, `РС_` и другие префиксы из `yaxunit-tests`, а
  не `Doc_`, `Spr_`, `CommonModule_` или транслитерации.
- Проверяй, что `[Имя объекта]` совпадает с точным именем объекта метаданных и
  не содержит неутверждённых сокращений.
- Проверяй, что helper'ы, переменные, fixture-поля, поля структур, имена
  тестовых методов и сценариев в YAxUnit тоже не заменяют объект метаданных
  локальным сокращением (`PO`, `Spec`, `Спец` и т.п.).
- Проверяй, что суффикс модуля соответствует тестируемому модулю: `_МО` для
  модуля объекта, `_ММ` для модуля менеджера, `_НЗ` для модуля набора записей;
  для общего модуля суффикс не добавляется.
- Проверяй, что имена тестовых методов описывают проверяемое поведение, а не
  техническую реализацию.
- Считай неверное именование тестового модуля `important`; повышай до
  `blocking`, только если из-за имени тест не обнаруживается, не запускается или
  ломает структуру тестового расширения.
- Не смешивай замечания по тестам с общими требованиями к business logic.

## Ограничения

- Не дублируй проверки Сонара.
- Не исправляй код автоматически в рамках review-mr.
- Не используй `rlm-tools-bsl` и связанные MCP-инструменты для discovery или
  выводов по MR.
- Фокусируйся на логике, архитектуре, рисках и конкретных предложениях.
- Не подменяй review личными предпочтениями без доказуемого риска.
- Если проблем нет, зафиксируй это явно, а не придумывай замечания.

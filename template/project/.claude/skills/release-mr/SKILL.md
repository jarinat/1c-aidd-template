# Release MR

Этот skill является ограниченным исключением из запрета `gitlab-tools` на
создание MR. Он не заменяет обычный workflow feature-MR и не применяется,
если проект не настроил релизный процесс.

## Source of truth

- shell policy: `.claude/rules/core/tool-usage.md`;
- git workflow: `.claude/rules/core/git-workflow.md`;
- project-local релизный контракт:
  `.claude/rules/project/ticketing.md`, раздел «Релизные MR»;
- треды, пайплайны и ограничения обычных GitLab-операций:
  `.claude/skills/gitlab-tools/SKILL.md`.

## Триггеры

- «подготовь релизные MR <версия>»;
- «собери описание релизного MR»;
- «создай релизные MR <версия>».

Запросы про review, комментарии, pipeline или feature-MR не являются
триггером: для них используй `gitlab-tools` или соответствующий AIDD skill.

## Границы

- Не выполняй сценарий, пока в `ticketing.md` не заполнен раздел «Релизные
  MR» или его статус — `disabled`. Покажи отсутствующие параметры и остановись.
- Не угадывай версию, ветки, remote, GitLab project, assignee, reviewer,
  tracker URL или формат описания: бери их только из project rules либо из
  явного запроса пользователя.
- Не approve, не merge, не включай auto-merge и не редактируй feature-MR.
- Не создавай и не меняй commit версии, если project rules не требуют этого
  явно: это отдельное изменение с собственным автором и проверками.
- Не публикуй MR при запросе только «подготовить». Если пользователь прямо
  попросил «создать» или совместил подготовку и создание, покажи состав и
  готовое описание до первой публикации; создавай только после явного
  подтверждения, если пользователь попросил внести правки.
- Используй `glab auth status` для проверки авторизации; не запрашивай и не
  сохраняй token.
- Соблюдай shell policy. Не используй inline shell для file inspection и не
  заменяй штатные GitLab-операции `curl`, `glab api` или временными JSON.

## Алгоритм

### 1. Проверить настройку и доступ

1. Прочитай раздел «Релизные MR» из `ticketing.md`.
2. Убедись, что нет placeholders и заполнены ветки, remote, GitLab project,
   источник состава, формат описания и assignment policy.
3. Определи версию из явного запроса или по разрешённому project rules
   формату текущей ветки. Если это невозможно — запроси версию.
4. Выполни `glab auth status` и убедись, что активный host и repo соответствуют
   project rules.
5. Получи актуальное состояние remote (`git fetch` только если это допускает
   project policy) и проверь чистоту рабочей копии. При не относящихся к
   релизу локальных изменениях не переключай и не переименовывай ветку.

### 2. Подготовить релизную ветку

1. Вычисли ожидаемые `Release branch` и, если задана, `Исходная ветка для
   переименования` по version format из project rules.
2. Если текущая ветка уже релизная, продолжай. Если разрешено переименование
   исходной ветки, сначала докажи, что:
   - нет открытого MR со старой source-веткой;
   - локальная и remote-ветка не разошлись;
   - целевая релизная ветка не существует локально или на remote.
3. Только после успешных проверок переименуй ветку и опубликуй новое имя по
   проектному контракту. При любом расхождении остановись и покажи его
   пользователю.

### 3. Определить состав релиза

1. Выполни проектно заданный `git-range-and-merge-filter` и получи merge
   commits между базовой и релизной веткой.
2. Исключи только типы merge/commit, явно перечисленные в project rules
   (например back-merge предыдущего релиза или технический version bump).
3. Из оставшихся feature-мерджей извлеки тикеты по `Project ticket prefix`.
4. Для каждого тикета найди соответствующий закрытый или merged feature-MR по
   `mr-ticket-matching-rule` и прочитай его описание через `glab mr`.
5. Если тикет, merge или MR нельзя сопоставить однозначно, не достраивай
   состав по догадке: покажи расхождение пользователю.

### 4. Собрать и показать описание

1. Сформируй описание основного MR по
   `release-description-format` из project rules.
2. Передавай в описание только проверенную суть feature-MR: без служебного
   мусора, неподтверждённых предположений и изменений, не вошедших в диапазон.
3. Добавь tracker links только если они разрешены настройкой проекта.
4. Покажи пользователю версию, ветку, состав тикетов, готовое описание,
   target branches и предполагаемые назначения.
5. Для запроса «подготовить» на этом остановись. Для запроса «создать» после
   показа переходи к публикации, если пользователь не запросил правки.

### 5. Создать и проверить MR

1. Создавай MR строго в порядке `target-branches` и с title из project rules.
2. У основного MR используй собранное описание; у остальных — только формат,
   прямо заданный project rules (например пустое описание).
3. Назначай assignee/reviewer исключительно по `assignment-policy`; не
   добавляй reviewer по умолчанию.
4. После каждого `glab mr create` прочитай созданный MR и проверь source,
   target, title, описание и назначения.
5. Сообщи ссылки на созданные MR, состав релиза и действия, которые остаются
   ручными (approve, merge, auto-merge при необходимости).

## Известные ловушки

- Номера MR не определяют порядок попадания изменений в релиз. Источник
  состава — только project-local git range и merge-filter.
- В диапазон может попадать back-merge предыдущего релиза; исключай его лишь
  когда правило проекта явно это описывает.
- Версионный commit не равен feature и не должен становиться пунктом описания.
- Нельзя переносить стиль описания, tracker URLs или назначений из другого
  проекта: это project-specific контракт.

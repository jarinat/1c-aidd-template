# БСП ВариантыОтчетов

Используй этот reference при создании, изменении, review или debug отчета,
который должен работать через подсистему БСП `ВариантыОтчетов`: панель
отчетов, предопределенные варианты, общая форма отчета, настройка формы,
хранилище вариантов или обновление справочника `ВариантыОтчетов`.

## Discovery

1. Найди существующие отчеты проекта, уже подключенные к `ВариантыОтчетов`.
   Сравнивай не только `.dcs`, но и `.mdo`, модуль менеджера, модуль объекта,
   project-wrapper переопределяемого модуля и runtime-обновление данных.
2. Определи способ внедрения:
   - полный: хранилище и общие формы заданы на уровне конфигурации;
   - частичный: свойства задаются на каждом подключаемом отчете.
3. Найди фактическую точку регистрации отчетов. В проектах она часто находится
   не прямо в поставочном модуле БСП, а в project-wrapper, который вызывается
   из переопределяемого модуля БСП.
4. Зафиксируй найденные project-specific имена как факты текущего проекта, а
   не как переносимые имена для других проектов.

## Чеклист подключения отчета

Для отчета на СКД, подключаемого к БСП `ВариантыОтчетов`, проверь:

- отчет имеет основную СКД-схему и рабочий вариант настроек с выбранными
  полями, структурой и сортировками, если они нужны;
- при частичном подключении у отчета задано хранилище вариантов:
  `SettingsStorage.ХранилищеВариантовОтчетов`;
- при частичном подключении у отчета заданы все общие формы БСП:
  `CommonForm.ФормаОтчета`,
  `CommonForm.ФормаНастроекОтчета`,
  `CommonForm.ФормаВариантаОтчета`;
- отчет зарегистрирован в проектной точке `НастроитьВариантыОтчетов` вызовом
  БСП `ВариантыОтчетов.НастроитьОтчетВМодулеМенеджера(...)` или локальным
  эквивалентом reference-проекта;
- в модуле менеджера отчета есть экспортная процедура
  `НастроитьВариантыОтчета(Настройки, НастройкиОтчета)`;
- каждый предопределенный вариант, который должен быть виден пользователю,
  зарегистрирован через `ВариантыОтчетов.ОписаниеВарианта(...)`;
- ключ варианта в БСП совпадает с именем варианта в СКД, если проектный
  reference pattern не доказывает иной контракт;
- представление варианта в СКД задано человекочитаемо: форма БСП может
  использовать именно представление текущего варианта как заголовок.

## Хуки формы отчета

Если отчет должен программно менять поведение общей формы БСП:

1. В `НастроитьВариантыОтчета` установи
   `НастройкиОтчета.ОпределитьНастройкиФормы = Истина`.
2. В модуле объекта реализуй экспортную процедуру
   `ОпределитьНастройкиФормы(Форма, КлючВарианта, Настройки)`.
3. Включи только нужные события формы, например:
   `Настройки.События.ПередЗагрузкойНастроекВКомпоновщик = Истина`.
4. Реализуй соответствующий экспортный обработчик в модуле объекта.
5. Если обработчик меняет схему компоновки данных перед загрузкой настроек
   (например, устанавливает доступные значения параметров или полей), заверши
   обработчик вызовом:

```bsl
ОтчетыСервер.ПодключитьСхему(ЭтотОбъект, Контекст, СхемаКомпоновкиДанных, КлючСхемы);
```

Без этого изменения схемы могут не попасть в компоновщик, даже если обработчик
фактически вызывается.

## Доступные значения отборов

- Для фиксированного набора значений используй статический `СписокЗначений`.
- Для строковых реквизитов, значения которых живут в данных, формируй список
  запросом к актуальным объектам ИБ.
- Не создавай собственную форму отчета только ради доступных значений, если
  общая форма БСП и хуки объектного модуля покрывают задачу.
- Если список пустой в UI, проверь не только сам запрос, но и весь контракт:
  общие формы отчета, `ОпределитьНастройкиФормы`, включенное событие,
  вызов `ОтчетыСервер.ПодключитьСхему`, обновление данных `ВариантыОтчетов` и
  клиентский кеш формы.

## Обновление данных в ИБ

Изменения в metadata отчета и вариантах СКД не всегда сразу отражаются в
справочнике `ВариантыОтчетов`.

- В разработке после добавления отчета, изменения хранилища, форм, ключа или
  представления варианта планируй ручное обновление данных справочника
  `ВариантыОтчетов` или другой принятый в проекте способ обновления
  вспомогательных данных.
- Не поднимай версию конфигурации только ради локального теста, если это не
  согласовано как часть задачи.
- При переименовании ключа варианта проверь старые записи справочника,
  пользовательские настройки, избранное, историю и клиентский кеш. Корректные
  metadata не гарантируют, что уже открытая форма сразу покажет новый заголовок.

## Validation

Минимальная проверка после изменения:

- свойства отчета: хранилище вариантов, общие формы, основная СКД, модуль
  менеджера и модуль объекта;
- состав СКД: вариант, выбранные поля, структура, параметры, отборы,
  сортировки и заголовки;
- project-wrapper `НастроитьВариантыОтчетов`: отчет зарегистрирован в той же
  точке, что и reference-отчеты;
- статическая проверка исходников/EDT по отчету и связанным модулям;
- runtime-проверка после обновления данных `ВариантыОтчетов`, если задача
  затрагивает видимость отчета, заголовок, варианты или доступные значения
  отборов.

Проверку можно выполнить через MCP, EDT UI, Designer, project-local helpers,
read-only diff или другой доступный в проекте способ. Важно доказать сам
контракт БСП, а не использование конкретного инструмента.

## Инструментальные ограничения

Если основной структурированный инструмент не умеет записать свойства вроде
`variantsStorage`, `defaultForm`, `defaultSettingsForm` или
`defaultVariantForm`:

1. Зафиксируй буквальный отказ инструмента.
2. Проверь документацию/возможности инструмента и фактическое состояние
   объекта другим доступным способом.
3. Убедись, что изменение уже входит в согласованный scope.
4. Примени XML fallback только по `.claude/rules/core/tool-usage.md`.
5. После fallback подтверди результат через повторное чтение metadata,
   статическую/EDT-валидацию и diff ожидаемых строк.

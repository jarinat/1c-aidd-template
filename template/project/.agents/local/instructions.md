# Личный AIDD-слой — инструкции Codex

## Назначение

Этот файл — личная надстройка над корпоративным agent layer MPL Systems.
Корпоративный `AGENTS.md` в корне репозитория читает его явно; сам `AGENTS.md`
принадлежит корпоративному слою и личным слоем не изменяется.

Надстройка не дублирует корпоративный слой: техническая процедура 1С/EDT живёт
только в skills `mpl-*`, здесь остаётся AIDD-специфика — workflow, артефакты
тикета и маршрутизация сценариев.

Источники истины личного слоя:

- `CLAUDE.local.md` — входная точка личного слоя, общая с Claude Code;
- `.claude/docs/onboarding-project.md` — сценарий обследования и настройки
  project-specific правил;
- `.claude/rules/core/*.md` — переносимые правила;
- `.claude/rules/project/*.md` — специфика текущего проекта;
- `.claude/rules/paths/*.md` — правила для отдельных зон дерева;
- `aidd/docs/*` — рабочие артефакты тикетов.

## Роль Codex

Codex выступает как независимый инженерный эксперт, а не как исполнитель,
который автоматически подтверждает предположения пользователя.

- Проверяй идеи на применимость к реальному проекту, AIDD-процессу и 1С/EDT.
- Отделяй факты из репозитория от догадок и проектных решений.
- Не превращай найденный пример в правило без подтверждения пользователя.
- Исправляй причину проблемы, а не только видимый симптом.
- Не смешивай project-specific правила с переносимым runtime-слоем.

## Режим работы с workflow

- Сначала предлагай существенные изменения workflow и жди подтверждения.
- Не редактируй `.claude/`, `aidd/` и этот файл молча, даже если изменение
  кажется очевидным.
- После подтверждения вноси правку сам и проверяй результат.
- Если пользователь явно просит подготовить файл или внести уже согласованную
  правку, действуй в рамках этого согласования.
- Не меняй бизнес-код в `src/` при задаче на настройку workflow, если это не
  является явной целью пользователя.

## Локальная политика

Личный слой — это `.claude/` (кроме корпоративных путей `mpl-*`), `aidd/`,
`CLAUDE.local.md` и `.agents/local/`. Он не версионируется в Git.

Корневой `AGENTS.md`, `.claude/rules/mpl/`, `.claude/skills/mpl-*` и `doc/ai/**`
к личному слою не относятся: они принадлежат корпоративному слою,
отслеживаются в Git и личным слоем не изменяются.

Не добавляй локальные пути в `.gitignore` или `.git/info/exclude` без явной
просьбы пользователя. Не готовь их к коммиту без отдельного указания.

## Project Onboarding

Если `.claude/rules/project/onboarding-status.md` отсутствует, имеет статус
`draft` или содержит незакрытые вопросы, не начинай крупную бизнес-задачу
вслепую.

Сначала предложи выполнить обследование проекта по сценарию:

```text
.claude/docs/onboarding-project.md
```

Во время onboarding:

- обследуй структуру репозитория, EDT-проекты, расширения, тесты, CI и README;
- выявляй кандидаты на правила, но помечай их как неподтвержденные;
- задавай пользователю вопросы там, где правило нельзя надежно вывести из
  репозитория;
- записывай только подтвержденные правила в `.claude/rules/project/*` и
  `.claude/rules/paths/*`;
- не запускай долгие операции, индексацию или изменение локальных MCP/BSL
  реестров без явного подтверждения.

## Границы слоев

- `core` — переносимые правила AIDD и общие инженерные правила.
- `project` — специфика текущего проекта: тикеты, naming, testing,
  change policy, known pitfalls.
- `paths` — ограничения для конкретных зон дерева.
- `skills` — исполняемые сценарии Claude Code.
- `agents` — роли subagent-ов Claude Code.
- `scripts` — project-local entrypoint scripts.
- `local` — личные и machine-specific настройки.
- `aidd/docs` — артефакты конкретных тикетов.

Для каждого правила должен быть один основной source of truth. Маршрутизация
EDT MCP задана корпоративным слоем и здесь не дублируется.

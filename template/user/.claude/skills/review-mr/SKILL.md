# Review Merge Request

Используй subagent `review-mr`.

Source of truth:

- общая политика code review:
  - `~/.claude/rules/core/code-review.md`
- специализированные проверки:
  - `1c-query`
  - `edt-form-editing`
  - `yaxunit-tests`

## Алгоритм

1. Проверь, что заданы `SOURCE_BRANCH` и `TARGET_BRANCH`.
2. Получи актуальный diff между ветками:
   - `git fetch origin $SOURCE_BRANCH $TARGET_BRANCH`
   - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH --stat`
   - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH --name-status --find-renames`
   - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH --find-renames`
3. Просмотри список затронутых файлов и оцени общий риск изменений.
4. Для рискованных изменений не ограничивайся только hunks из diff: прочитай
   окружающий метод, связанные процедуры, вызывающие места, модуль формы или
   тестовый модуль, если без этого нельзя уверенно оценить поведение.
5. Проведи review diff с фокусом на:
   - behavioural regressions и нарушения бизнес-логики;
   - явное дублирование и упущенное переиспользование;
   - читаемость, вложенность и перегруженные условия;
   - неоптимальные алгоритмы, запросы к базе в циклах и лишние обходы;
   - рассинхрон EDT-форм и связанного кода;
   - именование и структуру YAxUnit-тестов, если они затронуты.
6. Отдельно проверь добавленные строки кода на англоязычные операторы 1С вроде
   `If`, `Then`, `Else`, `Function`, `Procedure`, `Return`, `Try`, `And`, `Or`,
   `Break`, `Continue`, кроме комментариев, строковых литералов и частей
   идентификаторов. Для запросов 1С также проверяй англоязычные ключевые слова
   через skill `1c-query`.
7. Сгруппируй замечания по категориям:
   - `blocking` — неправильный результат, runtime-ошибка, потеря данных,
     критичная деградация производительности, сломанная форма, неработающий
     тест или грубое нарушение, после которого MR нельзя принимать;
   - `important` — доказуемый архитектурный, алгоритмический риск или риск
     поддерживаемости, который не обязан ломать поведение прямо сейчас, но
     должен быть исправлен до завершения работы;
   - `minor` — локальные улучшения читаемости и неопасные замечания без
     существенного риска для поведения.
8. Каждое замечание формулируй по фактам:
   - где найдено;
   - в чём проблема;
   - почему это важно;
   - как исправить или что проверить дополнительно.
9. Подготовь итоговый отчёт:
   - краткая статистика по diff;
   - список замечаний по категориям;
   - повторяющиеся проблемные паттерны, если они реально видны в MR;
   - явная фиксация, что замечаний нет, если review чистый.

## Специализированные проверки

### EDT-формы

- Если в diff затронут `Form.form`, проверяй не только XML, но и связь формы с
  кодом.
- Ищи рассинхрон между `name` и обращениями через `Элементы.<Имя>`.
- Ищи рассинхрон между `commandName` и секцией `<formCommands>`.
- Сопоставляй обработчики из `Form.form` с процедурами в `Module.bsl`.
- Проверяй уникальность новых `id` и корректность контейнера для нового
  элемента.

### YAxUnit

- Если в diff есть YAxUnit-тесты, отдельно проверяй именование тестовых
  модулей и методов через skill `yaxunit-tests`.
- Проверяй, что имя тестового модуля соответствует соглашению из
  `yaxunit-tests`: `[Префикс типа объекта]_[Имя объекта]{_Суффикс типа модуля}`.
- Проверяй, что используются кириллические префиксы типов объектов: `ОМ_`,
  `Док_`, `Спр_`, `Обр_`, `РН_`, `РС_` и другие префиксы из `yaxunit-tests`, а
  не `Doc_`, `Spr_`, `CommonModule_` или транслитерации.
- Проверяй, что `[Имя объекта]` совпадает с точным именем объекта метаданных и
  не содержит неутверждённых сокращений.
- Проверяй, что суффикс модуля соответствует тестируемому модулю: `_МО` для
  модуля объекта, `_ММ` для модуля менеджера, `_НЗ` для модуля набора записей;
  для общего модуля суффикс не добавляется.
- Проверяй, что имена тестовых методов описывают проверяемое поведение, а не
  техническую реализацию.
- Считай неверное именование тестового модуля `important`; повышай до
  `blocking`, только если из-за имени тест не обнаруживается, не запускается или
  ломает структуру тестового расширения.
- Не смешивай замечания по тестам с общими требованиями к business logic.

## Ограничения

- Не дублируй проверки Сонара.
- Не исправляй код автоматически в рамках review-mr.
- Фокусируйся на логике, архитектуре, рисках и конкретных предложениях.
- Не подменяй review личными предпочтениями без доказуемого риска.
- Если проблем нет, зафиксируй это явно, а не придумывай замечания.

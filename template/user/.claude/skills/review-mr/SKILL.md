# Review Merge Request

Используй subagent `review-mr`.

Source of truth:

- общая политика code review:
  - `.claude/rules/core/code-review.md`
- специализированные проверки:
  - `1c-query`
  - `edt-form-editing`
  - `yaxunit-tests`

## Алгоритм

1. Проверь, что заданы `SOURCE_BRANCH` и `TARGET_BRANCH`.
2. Получи актуальный diff между ветками:
   - `git fetch origin $SOURCE_BRANCH $TARGET_BRANCH`
   - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH --name-only`
   - `git diff origin/$TARGET_BRANCH...origin/$SOURCE_BRANCH`
3. Просмотри список затронутых файлов и оцени общий риск изменений.
4. Проведи review diff с фокусом на:
   - behavioural regressions и нарушения бизнес-логики;
   - явное дублирование и упущенное переиспользование;
   - читаемость, вложенность и перегруженные условия;
   - неоптимальные алгоритмы, запросы к базе в циклах и лишние обходы;
   - рассинхрон EDT-форм и связанного кода;
   - именование и структуру YAxUnit-тестов, если они затронуты.
5. Отдельно проверь добавленные строки на англоязычные операторы 1С вроде
   `If`, `Then`, `Else`, `Function`, `Procedure`, `Return`, `Try`, `And`, `Or`,
   `Break`, `Continue`, кроме комментариев и строковых литералов.
6. Сгруппируй замечания по категориям:
   - `blocking` — явные дефекты, критичные регрессии и грубые нарушения;
   - `important` — существенные архитектурные, алгоритмические и
     поддерживаемые риски;
   - `minor` — локальные улучшения читаемости и неопасные замечания.
7. Подготовь итоговый отчёт:
   - краткая статистика по diff;
   - список замечаний по категориям;
   - явная фиксация, что замечаний нет, если review чистый.

## Специализированные проверки

### EDT-формы

- Если в diff затронут `Form.form`, проверяй не только XML, но и связь формы с
  кодом.
- Ищи рассинхрон между `name` и обращениями через `Элементы.<Имя>`.
- Ищи рассинхрон между `commandName` и секцией `<formCommands>`.
- Сопоставляй обработчики из `Form.form` с процедурами в `Module.bsl`.
- Проверяй уникальность новых `id` и корректность контейнера для нового
  элемента.

### YAxUnit

- Если в diff есть YAxUnit-тесты, отдельно проверяй именование тестовых
  модулей и методов через skill `yaxunit-tests`.
- Не смешивай замечания по тестам с общими требованиями к business logic.

## Ограничения

- Не дублируй проверки Сонара.
- Фокусируйся на логике, архитектуре, рисках и конкретных предложениях.
- Если проблем нет, зафиксируй это явно, а не придумывай замечания.

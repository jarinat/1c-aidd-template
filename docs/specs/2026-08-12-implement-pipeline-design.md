# Конвейер mpl-implement: research, декомпозиция, состояние прогона

Дата: 2026-08-12
Статус: согласовано владельцем посекционно, реализация начата в тот же день
Репозиторий реализации: `EDT-project-template`, ветка `feature/team-ai-tools-v2`

## Задача

Достроить корпоративный конвейер реализации до полного:

```
вход → gate R → [mpl-research] → gate D → [mpl-tasks] → цикл по блокам (mpl-implementer)
```

Сейчас существует только правый конец цепочки: skill `mpl-implement` и роль
`mpl-implementer`. Шаг «раздели на блоки» описан в оркестраторе тремя
предложениями, исследование кодовой базы не описано вовсе, состояние прогона
нигде не сохраняется.

## Решения владельца, принятые ранее (вход этой спеки)

1. Имя skill декомпозиции — `mpl-tasks`.
2. `mpl-research` возвращает структуру, а не пишет процессный артефакт.
3. Fast path gate — по проверяемым признакам, а не по оценке размера задачи.

## Решения этой сессии

### Р1. Вопрос 4: шаг 2 `mpl-implement` — вариант А с точной границей

Шаг 2 сейчас смешивает три разные вещи; они расходятся по разным адресам:

| Что | Куда | Почему |
|---|---|---|
| Gate «нужна ли декомпозиция» | остаётся в `mpl-implement` | решение оркестратора, а не метод нарезки |
| Метод нарезки | уезжает в `mpl-tasks` | предмет отдельного skill |
| Контракт блока как условие приёмки | остаётся в `mpl-implement` | нужен и на fast path, где `mpl-tasks` не открывается |

Опасен самодостаточный **метод**: короткий текст в оркестраторе выигрывает у
ссылки, и `mpl-tasks` никто не откроет. Перечень полей приёмки методом не
является — прочитав его, агент не получает ложного ощущения, что умеет резать.
Определение блока живёт в `mpl-tasks`; `mpl-implement` его не переписывает.

Цена: на крупной задаче добавляется одно чтение skill. Gate делает эту цену
условной.

### Р2. У `mpl-tasks` роли нет

Роль оправдана, когда изоляция даёт то, чего нет у оркестратора:
`mpl-implementer` даёт границу scope, `mpl-researcher` — экономию контекста.
Декомпозиция не даёт ни того, ни другого: файлов не меняет, объёмного discovery
не порождает, а её результат обязан целиком лечь в контекст оркестратора.
Изолировать производителя от единственного потребителя его полного вывода —
потерянный контекст. У Codex ролей нет вовсе, там такая роль — чистый оверхед.

### Р3. Гранулярность `mpl-researcher` — единый контракт, scope задаёт вызывающий

На входе: контекст задания + перечень того, что надо выяснить. Если вопросов
ещё нет, scope = само задание. Уточняющие прогоны — тот же контракт с более
узким scope. Режимов внутри роли нет.

Отвергнуто: два режима (`reconnaissance` / полный research) — режимы расходятся,
а «до PRD» корпоративному слою сказать нечем. Отвергнуто: одна неизвестность на
вызов — чтобы перечислить неизвестности, их надо сначала обнаружить.

Ключевое следствие: именно scope на входе делает измеримой экономию контекста и
даёт якорь для жёсткого контракта вывода.

### Р4. Классификация неизвестностей — новый стандарт `doc/ai/standards/autonomy.md`

Правило сквозное: по нему `mpl-researcher` заполняет открытые решения,
`mpl-implementer` решает между `blocked` и «дожать самому», `mpl-tasks` —
между blocker на research и вопросом человеку. Значит его место не в одном из
трёх потребителей.

Отвергнуто: `agent-tools.md` (стандарт про выбор инструмента, «кому адресован
вопрос» туда не ложится); роль `mpl-researcher` (дало бы обратную зависимость
двух других skills от роли исследователя).

Цена: десятый стандарт и +1 строка в всегда загружаемом роутере `AGENTS.md`.
Признана оправданной: правило поведенческое и срабатывает на каждой задаче.

Список адресатов (`developer-owner`, `analyst`, `data-owner`, …) наверх **не**
поднимается — это ролевая модель конкретной команды. Наверх идёт требование
«назови адресата и причину».

### Р5. Два независимых гейта, а не один каскад

Крестное произведение реально, поэтому один гейт врёт:

| | декомпозиция не нужна | нужна |
|---|---|---|
| research не нужен | вход называет файл и правку | вход называет все точки, правок много |
| research нужен | однострочная правка в неизвестном месте | обычный крупный случай |

Гейт D оценивается **после** research: research регулярно превращает «одну
правку» в двенадцать точек.

**Gate R** — research обязателен, если верно хотя бы одно:

- вход не называет конкретные затронутые файлы/точки встраивания;
- нужен технический источник (реквизит, поле, метод, настройка СКД, роль,
  форма), который во входе не назван;
- задание удаляет или переименовывает элементы метаданных.

**Gate D** — декомпозиция обязательна, если верно хотя бы одно:

- затронуто больше одного implementation-файла (плюс один тестовый/fixture не
  считается);
- diff не описывается одним предложением;
- вводятся новые объекты метаданных, реквизиты, поля, роли, подсистемы, обмены,
  публичные API или миграции данных;
- есть удаление или переименование метаданных;
- research вернул незакрытые решения для человека.

Ни один признак не требует оценки размера.

Гейты принадлежат `mpl-implement`. Вызванные напрямую, `mpl-research` и
`mpl-tasks` гейты не прогоняют: человек уже решил, что ему нужно. Так
сохраняется инвариант «каждый skill вызывается независимо».

### Р6. Контракт вывода роли `mpl-researcher` — шесть полей

```yaml
status: complete            # complete | partial | blocked
findings:
  - scope_item: что выясняли
    verdict: confirmed      # confirmed | candidates | not_found | blocked
    evidence: [ путь:строка, имя объекта метаданных, инструмент MCP + запрос ]
    notes: одно-два предложения вывода
entry_points:
  - path: файл
    what: что именно здесь придётся менять
risks:
  - что сломается за пределами точек встраивания и почему
open_decisions:
  - unknown: ...
    class: по autonomy.md
    checked: что уже проверено и чем
    evidence: ...
    why_human: почему нельзя вывести из кода
tooling_gaps: []
```

Четыре решения внутри контракта:

1. `verdict` из четырёх значений — машинная проверяемость research.
2. `not_found` без перечня проверенного не принимается: в `evidence` при этом
   вердикте лежат проверенные каталоги, типы файлов, объекты и инструменты.
3. `evidence` — якорь, а не цитата. Фрагменты исходников длиннее строки в вывод
   не попадают; без этого правила экономии контекста нет.
4. Расхождение входа с кодом отдельного поля не получает — всегда
   `open_decisions`. Конфликт, который агент вправе решить сам, конфликтом не
   является; раз решение за человеком, ему место среди решений.

Намеренно **нет**: рекомендаций по реализации и плана проверки. Оба — уже
проектирование; иначе `mpl-tasks` наследует чужие решения без источника.

### Р7. Контракт блока `mpl-tasks`

```yaml
blocks:
  - id: 1
    kind: change              # change | verification
    goal: что делает блок
    scope: [ пути, которые блок вправе трогать ]
    done_when: критерий готовности, проверяемый снаружи блока
    verification:
      - command: ...
        by: implementer       # implementer | orchestrator | human
      - manual: ...
        by: human
    reference: ближайший локальный образец   # необязательно
coverage:
  - requirement: требование из входа
    block: 1
    check: чем закрыто
blockers: []
```

- `scope` как перечень путей делает проверку «diff вышел за блок» механической;
  он же становится списком явных путей для `mpl-commit`.
- `verification` допускает `manual`, но не допускает пустоту. Контракт,
  требующий исполняемой команды всегда, спровоцировал бы агента её выдумать.
  Блок без проверки — не блок: укрупняй или возвращай blocker.
- `depends_on` намеренно нет: блоки строго последовательны, порядок в списке и
  есть зависимость.
- `coverage` — защита от тихой потери части задания; непокрытое требование без
  явного решения об отсрочке даёт `blockers`.

Метод нарезки (уехал из шага 2 `mpl-implement`): границу блока проводи там, где
проходит граница проверки, а не там, где кончается файл; блок самодостаточен;
один блок — будущая единица коммита; после удаления/переименования метаданных
обязателен `kind: verification`; наследуй только подтверждённые решения;
недостающий проверяемый факт — blocker на research, а не вопрос человеку.

### Р8. YAxUnit запускает оркестратор

Граница общая, а не про тесты: **исполнитель запускает проверки, не выходящие
за рабочее дерево** (синтаксис, линт, валидация EDT в режиме чтения, проверка
запроса); всё, что меняет ИБ, пересобирает проект или трогает общий ресурс,
запускает оркестратор.

Обоснование не «субагент не может спросить человека» (у команды личные базы
разработчика, этот довод снят), а **двойной прогон**: шаг 4 `mpl-implement`
обязывает оркестратора самому запустить проверки блока. Если тот же прогон
делает исполнитель, на каждом блоке выходит два обновления конфигурации ИБ
подряд. Ослабить требование к оркестратору нельзя — это ядро контроля.

Исключение «блок про тесты» рассматривалось и отвергнуто: оно вводило второе
правило ради одного round-trip и давало исполнителю право на необъявленный
цикл отладки.

Прогон выполняется **без вопросов**, включая принудительное завершение сеансов,
если проектное правило объявляет ИБ разработчика личной. Условие остаётся явным:
корпоративный слой поедет и в проект с общей тестовой базой.

По умолчанию — один verification-блок в конце: стоимость определяется
обновлением конфигурации ИБ, а не самими тестами.

### Р9. Состояние прогона и возобновление

Решение 2 запрещает корпоративному слою нести **процесс** (этап, статус,
согласование). Дамп последнего вывода агента — не процесс, а **состояние
прогона**: ни статусов, ни согласований, ни этапов. Кэш, а не артефакт.

```
.agents/state/<task>/research.md   ← пишет оркестратор по выводу mpl-research
.agents/state/<task>/tasks.md      ← блоки от mpl-tasks + статус каждого блока
```

- Файлы `.md`, а не YAML: парсера нет ни у того, ни у другого — читает LLM,
  значит машиночитаемость не покупает ничего, а платим читаемостью для человека
  и разнобоем со слоем. Handoff роли остаётся YAML, потому что там строгость и
  есть весь смысл. Разделы `.md` называются теми же именами, что поля контракта.
- Прогресс хранится **внутри** `tasks.md`, а не отдельным файлом: блок и его
  статус рядом, рассинхрон по `id` при перенарезке становится невозможен, и это
  уже проверенная в личном слое конструкция.
- `.agents/state/` gitignored: это состояние машины, и в нём могут оказаться
  выдержки из кода.
- `research.md` накапливается: уточняющие прогоны дописывают findings по новым
  пунктам scope. Перезапись целиком потеряла бы первый проход.
- Уникальность `<task>` — ответственность вызывающего: корпоративный слой
  формата тикета не знает.

### Р10. Закрепление блока коммитом

`tasks.md` как единственное хранилище состояния имеет дыру: он говорит «блок 3
готов», но при обрыве в середине блока 4 рабочее дерево содержит правки обоих.
Коммит после блока закрывает это точно: незакоммиченное — ровно и только
незавершённая работа.

Три ограничения:

1. **Авторизация один раз на прогон.** Инвариант «commit — явное действие
   человека» остаётся; меняется лишь то, что «явно» говорится один раз в начале.
   Без авторизации конвейер работает по-прежнему, восстановление грубее. Push —
   никогда.
2. **Коммитит оркестратор через `mpl-commit`, роль — никогда.** Поле `scope`
   блока и есть перечень явных путей для помощника коммита.
3. **Порядок:** реализация → проверки → коммит → запись статуса. Отсюда:
   **источник истины о выполненных блоках — история git, `tasks.md` — кэш.**
   При возобновлении сначала сверь кэш с фактическими коммитами; при
   расхождении прав git.

Это единственное место, где новый конвейер **расширяет** полномочия слоя. Всё
остальное — сужения.

## Находки о машинерии

### Н1. Read-only роль сейчас невыразима технически

Renderer выдаёт всем ролям одну политику, валидатор её жёстко проверяет:
`permissionMode: acceptEdits`, никакого allowlist `tools`, фиксированный
denylist (`Agent, Task, WebFetch, WebSearch, EnterWorktree, ExitWorktree,
NotebookEdit`). `Edit` и `Write` в denylist не входят. Поле `capabilities`
проверяется только deny-list'ом опасных значений и на генерацию не влияет.

Значит сгенерированный `mpl-researcher` смог бы править файлы, а его read-only
осталась бы прозой — при том что в `mpl-implement` записано, что у Claude
границы роли обеспечены механизмом.

Правка, обратно совместимая:

- renderer сопоставляет `capabilities` → `disallowedTools`: роль без `edit`
  получает дополнительно `Edit` и `Write`;
- `permissionMode` остаётся `acceptEdits` у всех (валидатор требует точного
  совпадения; при запрещённых `Edit`/`Write` режим безвреден);
- валидатор получает проверку: роль без `edit` ⇒ её агент запрещает `Edit` и
  `Write`. Существующая проверка denylist работает на вхождение обязательного
  набора, лишние значения её не ломают.

`mpl-implementer` объявляет `edit`, поэтому его сгенерированный агент не
меняется.

### Н2. Решение 1 в буквальной формулировке невыполнимо

Решение 1 требует оговорить в описании `mpl-tasks` отличие от личного skill с
указанием пути `aidd/docs/tasklist/`. Контентный block-list валидатора режет в
корпоративных файлах `aidd`, `tasklist`, `PRD`, `active_ticket` без учёта
регистра — буквальный текст не прошёл бы собственную проверку слоя.

Формулировка, сохраняющая смысл без запрещённых токенов:

> Этот skill возвращает блоки вызывающему и не ведёт артефакты чужого рабочего
> процесса. Если в твоём личном слое есть похожий шаг, пишущий файл с этапами и
> статусами, — это его дело, а не этого skill.

## Состав изменений

Создаётся:

| Файл | Примечание |
|---|---|
| `doc/ai/standards/autonomy.md` | классы неизвестности и правило вопроса человеку |
| `.agents/skills/mpl-research/SKILL.md` | канонический |
| `.agents/skills/mpl-tasks/SKILL.md` | канонический |
| `.claude/skills/mpl-research/SKILL.md`, `.claude/skills/mpl-tasks/SKILL.md` | генерируются renderer'ом |
| `.agents/roles/mpl-researcher/ROLE.md` | `capabilities` без `edit` |
| `.claude/agents/mpl-researcher.md` | генерируется renderer'ом |

Правится:

- `tools/ai/mpl-render-claude-layer.sh` — mapping capabilities → disallowedTools;
- `tools/ai/mpl-validate-agent-layer.py` — `STANDARDS` += `autonomy`; проверка
  read-only роли;
- `tools/ai/tests/` — golden-случаи на обе новые проверки;
- `.agents/skills/mpl-implement/SKILL.md` — гейты, вызовы двух skills,
  состояние, возобновление, YAxUnit, закрепление коммитом; уходит фраза «не
  коммить в рамках этого skill»;
- `.agents/roles/mpl-implementer/ROLE.md` — из шага 4 уходит YAxUnit, появляется
  граница «проверки, не выходящие за рабочее дерево»;
- `AGENTS.md` — строка стандарта, две строки маршрутизации, две строки таблицы
  skills, строка роли в «Роли и агенты»;
- `doc/ai/README.md` — «Указатель ролей и агентов» обязан назвать новую роль;
- `.gitignore` — `.agents/state/`.

## Порядок реализации

1. `autonomy.md` + `AGENTS.md` + `STANDARDS` в валидаторе — ни от чего не зависит.
2. Машинерия read-only роли (renderer + валидатор + self-tests) — до появления
   роли, иначе первая же генерация даст неверный агент.
3. `mpl-research` + роль `mpl-researcher` + каталоги + генерация.
4. `mpl-tasks` + генерация.
5. Правки `mpl-implement` и `mpl-implementer` — последними: они ссылаются на всё
   предыдущее.

После каждого блока: `python3 tools/ai/mpl-validate-agent-layer.py`,
`bash tools/ai/mpl-render-claude-layer.sh --check`,
`bash tools/ai/tests/run-selftests.sh`.

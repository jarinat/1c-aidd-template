## Задача

Проектный слой сейчас — один плоский файл `doc/ai/project/project-rules.md`
(в шаблоне лежат только `project-rules.template.md` и
`project-rules.example.md`; ни один проект его ещё не заполнил). Правила,
которые действуют лишь для части дерева — исходники основной конфигурации,
расширения, тесты, generated-каталоги, tooling, — в такой форме либо тонут в
общем списке фактов, либо не пишутся вовсе.

Нужен проектный слой правил, привязанных к путям, который одинаково работает у
Claude Code и Codex.

## Что решено и почему

### Цель — маршрутизация, а не экономия контекста

Первичная боль — чтобы правило зоны **сработало**: агент должен узнать, что для
файла под путём X есть особые правила. Экономия контекста вторична и получается
побочно из той же конструкции (короткий роутер + отдельные файлы, читаемые по
применимости).

Основания:

- Проектные path-правила мелкие. В доноре (личный слой MBS,
  `.claude/rules/paths/`) семь файлов: `cf.md` — 24 строки, `yaxunit.md` — 36.
  Совокупно около двухсот строк. Контекст в этом репозитории расходуется не
  здесь.
- Ленивая загрузка даёт экономию ценой пропусков. Правило с `paths:` у Claude
  срабатывает, когда агент **трогает** подходящий файл, а решения «нужен ли
  тест», «это интеграционный контракт», «можно ли править каталог»
  принимаются до и часто без открытия файла из этой зоны.
- Корпоративный слой уже реализует экономию другой конструкцией: всегда
  загружен только короткий router в `AGENTS.md`, стандарты и skills читаются по
  необходимости. Path-слой следует тому же образцу.

### Асимметрия нативных механизмов (важно для будущего этапа 2)

- **Claude Code** поддерживает path-scoped правила нативно: `.claude/rules/**.md`
  с ключом `paths:` во frontmatter, подкаталоги обнаруживаются автоматически,
  правило с `paths:` грузится лениво при обращении к подходящему файлу.
  Источники: `https://code.claude.com/docs/en/claude-directory`,
  `https://code.claude.com/docs/en/memory`.
- **Codex** скоупит вложенные `AGENTS.md` по **текущему рабочему каталогу**, а не
  по трогаемому файлу (это зафиксировано в корневом `AGENTS.md` слоя со ссылкой
  на официальную документацию Codex). В 1С-репозитории агент почти всегда
  работает из корня, поэтому для path-scoping вложенный `AGENTS.md` практически
  инертен.

Следствие: «рендер в обе нативные проекции» может дать нативность только
Claude. Для Codex единственный работающий путь — инструкция роутера. Это
понижает ценность этапа 2 и подтверждает решение ограничиться этапом 1.

### Скоуп

Только этап 1. Этап 2 (рендер в `.claude/rules/project/*.md`, разыгнорирование
`.claude/`, расширение renderer и self-tests) не входит и запускается только
если наблюдения покажут, что роутер игнорируется.

## Дизайн

### 1. Артефакты

Шаблон поставляет каталог `doc/ai/project/paths/`:

| Файл | Владелец | Назначение |
|------|----------|------------|
| `doc/ai/project/paths/README.md` | корпоративный | объяснение механизма + таблица-роутер |
| `doc/ai/project/paths/sources.example.md` | корпоративный | разобранный пример зоны |
| `doc/ai/project/paths/<зона>.md` | проект | фактические правила зоны |

Таблица-роутер живёт в `paths/README.md`, а не в `project-rules.md`. Причины:
`project-rules.md` — файл фактов на четыре корзины, структуру которых валидатор
уже держит, и вставка навигационной таблицы трогала бы проверенную структуру;
плюс агент не должен читать большой файл фактов ради указателя.
`project-rules.template.md` получает одну строку-указатель на `paths/README.md`.

### 2. Формат path-файла

```markdown
---
paths:
  - "src/cf/**"
  - "src/cfe/*/**"
---

# Исходники основной конфигурации

- правило
- правило
```

Требования к frontmatter:

- открывается и закрывается строкой `---`;
- ровно один ключ — `paths`;
- значение — блочный YAML-список, непустой;
- каждый элемент — непустая однострочная строка без управляющих символов;
  кавычки вокруг глоба допустимы и снимаются при разборе;
- ничего кроме этого не поддерживается.

Синтаксис намеренно совпадает с нативным форматом Claude Code: файл остаётся
буквально переносимым в `.claude/rules/`, если этап 2 когда-нибудь понадобится.

### 3. Таблица-роутер

В `paths/README.md`:

```markdown
| Пути | Правило | Что регулирует |
|------|---------|----------------|
| `src/cf/**`, `src/cfe/*/**` | [sources.md](sources.md) | исходники конфигурации и расширений |
```

Файлы с маркером `.example.` в таблицу не входят и из сверки исключаются в обе
стороны — этот маркер уже несёт смысл «поставляемый пример» в слое
(`project-rules.example.md`).

Разбор колонки путей: глобы перечисляются через запятую, каждый в обратных
кавычках. При сверке кавычки и пробелы снимаются, результат сравнивается с
frontmatter как **множество**, поэтому порядок перечисления значения не имеет.

Пустая таблица легальна: свежий проект после merge шаблона имеет каталог
`paths/` с `README.md` и примером, но ни одного собственного правила. Это
корректное состояние, а не нарушение.

### 4. Якорь в AGENTS.md

В раздел `### Всегда действующие инварианты` добавляется один пункт: перед тем
как **планировать или менять** файл, сверься с таблицей путей проекта в
`doc/ai/project/paths/README.md` и прочитай каждое правило, чьи глобы совпадают
с путём; проектное path-правило уточняет корпоративный стандарт, но не отключает
skill `mpl-*` и правило безопасности.

Формулировка про «планировать» намеренна: она и есть причина, по которой
конструкция не полагается на ленивую загрузку.

### 5. Инварианты валидатора

Новые проверки в `tools/ai/mpl-validate-agent-layer.py`:

1. `doc/ai/project/paths/README.md` и `doc/ai/project/paths/sources.example.md`
   входят в обязательный инвентарь (существуют и отслеживаются Git).
2. Frontmatter каждого `doc/ai/project/paths/*.md` кроме `README.md`
   разбирается и соответствует требованиям раздела 2.
3. Таблица `README.md` и фактические файлы согласованы в обе стороны:
   нет path-файла без строки таблицы, нет строки таблицы без файла, и
   **множества глобов совпадают** — не просто наличие строки.
4. `AGENTS.md` не потерял инвариант из раздела 4 (проверка по образцу
   существующих safety-проверок секции маршрутизации).

Разбор блочного списка — отдельная небольшая функция. Существующий
`parse_frontmatter` намеренно отвергает списки и flow-коллекции, потому что
охраняет frontmatter skills; ослаблять его нельзя.

### 6. Побочный дефект, закрываемый здесь же

Контентные сканы валидатора (`corporate_files`) обходят весь `doc/ai`, включая
`doc/ai/project/`. Заполненный проектный файл уронил бы валидатор:
`FORBIDDEN_PROJECT` забанит имя проекта, `FORBIDDEN_WORKFLOW` — слова `PRD`,
`tasklist`, `AIDD`, которые в проектном слое законны. Дефект латентный только
потому, что `project-rules.md` пока нигде не заполнен.

Правка: под `doc/ai/project/` в корпоративные сканы попадают только
`*.template.md` и `*.example.md` — это корпоративные поставки и они обязаны
оставаться нейтральными. Всё остальное принадлежит проекту и из корпоративных
контентных сканов исключается.

Проверки существования, отслеживания и битых ссылок при этом продолжают
действовать на весь `doc/ai` — исключение касается только block-list сканов
содержимого и языкового guard.

### 7. Тесты

Self-tests (`tools/ai/tests/run-selftests.sh`) получают негативные случаи:

- path-файл без frontmatter;
- path-файл с пустым или неразбираемым списком `paths`;
- path-файл с лишним ключом во frontmatter;
- глобы файла разошлись с таблицей;
- path-файл не назван в таблице;
- строка таблицы ведёт в несуществующий файл;
- `AGENTS.md` потерял инвариант по path-правилам.

Позитивный случай: проектный path-файл, содержащий имя проекта и слово `PRD`,
проходит валидатор — прямое доказательство правки раздела 6.

## Границы

Не входит в Б2:

- рендер в `.claude/rules/project/*.md` и разыгнорирование `.claude/` (этап 2);
- миграция семи path-правил личного слоя MBS в проектный слой;
- path-scoping в корпоративном слое — корпоративные правила остаются
  переносимыми и path-agnostic по определению из `layers.md`.

- Roadmap обновлён: Б2 закрыт, зафиксирована асимметрия механизмов Claude/Codex
